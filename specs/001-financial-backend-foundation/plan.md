## Summary

Build exact USDT contracts/arithmetic, one Baghdad calendar, and a small source-aware transactional ledger. Six persistence models retain four wallet components, immutable financial operations/postings, request aliases, original reservation allocations and required audit. PostgreSQL constraints, ordered locks and bounded conflict handling protect atomic financial effects and future owning-domain writes.

P01 implements internal credit, purchase-purpose debit, withdrawal-purpose reservation, safe release, correction and read-only reconciliation primitives. It adds no financial HTTP endpoint or frontend integration. Business workflows, wallet provisioning at registration, subscription/referral awards, tasks, providers, queues, signing, payout settlement and recovery remain in their specified later phases.

## Design

### Money and time

[Financial boundary](contracts/financial-boundary.md) owns canonical amount/rate/source/date schemas once. Parse/format exact units without Number/parseFloat or global BigInt JSON hooks. Every stored component and derived total fits the spec limit; BigInt percentage multiplication may exceed int64 transiently before flooring/checking the final result.

Luxon is server-only with explicit Asia/Baghdad, prevalidated lexical/date/instant inputs and invalid-result checks. Its permissive ISO parser and isValid do not enforce the contract: check supported years 0001-9999 for Baghdad calculations and converted UTC output, explicit offsets, millisecond precision and non-null serialization. Use ISO weekdays 1-5, not locale weekend defaults. Task 12:00 inclusive/18:00 exclusive; first subscription date follows purchase cutoff; count 365 work dates including date one; expire at following calendar midnight even if Saturday. Count every weekday hour. New-dispatch normalization remains separate from expiry and weekend credit/reconciliation.

Positive counted-hour extensions use the [financial boundary](contracts/financial-boundary.md#counted-hour-extension-precision): its shared browser-safe validation/conversion owner scans plain decimal text, normalizes redundant zeros only for exact arithmetic, and calculates coefficient * 3,600,000 / 10^scale with BigInt. Reject any nonzero remainder, nonpositive duration or unsupported resulting deadline without rounding or mutation. A normalized maximum of eight integer and seven fractional digits bounds conversion while preserving every duration representable within years 0001-9999; it is not a raw spelling restriction or commercial limit. Only after exact/safe bounds checks may integer milliseconds enter Luxon. Keep counted residuals in integer milliseconds, split at Baghdad weekday boundaries, and add to the existing deadline. `"1.5"` is 5,400,000 counted ms, `"0.0000025"` is 9 ms, while `"0.0000001"` and `"0.000001"` are rejected. No floating-point-hour arithmetic.

### One financial boundary

The [internal contract](contracts/ledger-service.md) defines a transaction runner and transaction-bound primitives. The same Prisma.TransactionClient reaches authorization, financial effects and owning-domain writes. No root-client fallback, nested transaction or external I/O. Retryable callbacks must be database-only; duplicate recovery skips mutation callbacks.

Use Prisma 7 interactive Serializable transactions and static parameterized row locks. Lock relevant account/authority rows deterministically, then sorted declared wallet IDs, then reservation rows. Later domain callers must join this lock order for their own state. Initial maxWait=5 seconds and timeout=10 seconds require real integration validation. At most three full attempts for P2034; additionally classify exact structured serialization/deadlock SQLSTATE only if real adapter tests establish its shape. Never retry broad P2010, uniqueness errors or message substrings.

After locks, recheck current mutation authority, calculate complete allocations/outcomes, and save a validated walletBefore snapshot and the kind-specific source/direction/eligibility/allocation terms in the existing acceptedTerms JSON. Insert an immutable completed operation, then commit its postings/projections/reservation/dependent domain writes/audit together. Compare before plus expected posting deltas with the recorded walletAfter result; no new model, sequencing framework or public projection is introduced. No durable pending operation is committed. Losing replies are recovered by identity; unresolved conflicts are never success. Resolve only known business/request uniqueness conflicts after leaving the aborted transaction with a fresh authorized lookup.

Correct only available funds in an explicit source, through a new operation with reason/original reference and current ADMIN authority. No historical edit, reserved-fund debit, referral relabeling, task-approval reversal, fabricated receipt or payout settlement.

### Identity, release and reconciliation

Business identity and request aliases are independent. Canonical consequential intent includes operation, wallet, amount/source/origin and relevant immutable request terms; hash it deterministically. Exclude the supplied key, observed clock, mutable walletBefore balances and changing runtime eligibility. Save original accepted snapshots/result, including the accepted eligible-source grant, without reinterpreting them on replay. Reauthorize observation before replay; return the original result rather than current balances. Bind a new supplied replay key as identity bookkeeping only, with no new posting/domain effect/mutation audit.

Allocation state is ACTIVE -> RELEASED only in P01. Save exact gross/non-referral/referral amounts. Release requires a trusted owning-domain safe-state guard inside the same transaction and a conditional transition; browser booleans and uncertain replies cannot authorize it. P10/P11 add their full workflow/consumption, outside this phase.

Reconcile a scoped wallet through Prisma's existing interactive RepeatableRead transaction. Execute static `SET TRANSACTION READ ONLY` as its first callback statement, before observation-authorization/data reads; Prisma has no readOnly transaction option. In one snapshot compare exact ledger source/state sums, wallet components and ACTIVE allocation sums. PostgreSQL numeric/text aggregates preserve cumulative history beyond int64; validate integer text and parse as BigInt, never Number.

CHK035 additionally scans every scoped FinancialOperation, including operations with no postings. The [internal contract](contracts/ledger-service.md#reconciliation-errors-and-diagnostics) specifies each kind's exact expected source posting map, magnitude, origin, required accepted terms, before/after result, audit and reservation/opening/release agreement. Detect absent or extra source rows, wrong totals/directions/allocations and malformed snapshots even when wallet-level aggregates agree. Original source-order evidence comes from the immutable recorded before snapshot and accepted grant, not timestamp ordering or current eligibility. Return bounded authorized discrepancy records identifying the affected operation/allocation and safe category; no raw JSON, hashes, driver details, repair or guessed balances.
