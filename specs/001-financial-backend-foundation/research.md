# P01 Research Decisions

**Date**: 2026-10-02 | **Scope**: PLAN only | **Feature**: [spec.md](spec.md)

Existing source supplies auth, generic Decimal serialization, UTC date-only validation and auth persistence, but no financial models/services/contracts or Baghdad policy. This targeted PLAN amendment resolves the accepted CHK010 duration policy and CHK035 reconciliation design; it preserves unrelated decisions and leaves implementation/runtime evidence unexecuted.

## Exact money

- **Decision**: JavaScript BigInt and Prisma BigInt/PostgreSQL bigint hold micro-USDT. Browser-safe shared Zod schemas own canonical syntax/range; server code converts validated strings and performs bounded arithmetic. Maximum nonnegative units are `9223372036854775807`. Signed postings use the same maximum magnitude; zero is unsigned. Percentage intermediate multiplication may exceed int64 before flooring/checking the result.
- **Rationale**: Exact six-decimal ownership without a new money dependency, floating-point conversion or global JSON hooks. Each component and the derived total must fit the bound.
- **Alternatives considered**: Existing `core/serialization/decimal.ts` has generic precision, no micro-unit bounds; numeric JSON loses authority precision; another schema/parser owner would drift.
- **Evidence**: Contracts exports, existing Decimal helper, database schema/manifests; [Prisma 7 BigInt](https://www.prisma.io/docs/orm/v7/prisma-client/special-fields-and-types#working-with-bigint), [PostgreSQL 18 numeric types](https://www.postgresql.org/docs/18/datatype-numeric.html).

## Baghdad calendar dependency

- **Decision**: Retain API-only `luxon@3.7.2` and development `@types/luxon@3.7.6` in `core/business-calendar/business-clock.ts`. Validate the shared strict date/explicit-offset/millisecond instant grammar before Luxon's permissive ISO parser. Use explicit `Asia/Baghdad`, ISO weekdays 1-5, local calendar days/midnights and UTC output; check supported years 0001-9999 at input, intermediate Baghdad date and converted output boundaries in addition to isValid and non-null serialization. Do not infer weekends from locale or hardcode UTC+3.
- **Rationale**: The roadmap requires a maintained timezone-aware library and none exists in current manifests/lockfile. Domain counting remains our policy: task window, 365 work dates and weekday hours are distinct calculations.
- **Alternatives considered**: Handbuilt Intl offset inversion adds risk; elapsed Date addition ignores weekends; separate calendars drift. Temporal polyfill/date-fns timezone tooling add dependencies without a simpler P01 boundary.
- **Evidence**: Read-only pinned [Luxon metadata](https://registry.npmjs.org/luxon/3.7.2) and [typings metadata](https://registry.npmjs.org/@types%2Fluxon/3.7.6) confirm Node >=12 and TypeScript >=5.6; actual Node 24.18.1/pnpm 11.17.0 and manifest TypeScript 5.9.3 match. [Pinned DateTime source](https://github.com/moment/luxon/blob/3.7.2/src/datetime.js), [ISO parser](https://github.com/moment/luxon/blob/3.7.2/src/impl/regexParser.js), [date utilities](https://github.com/moment/luxon/blob/3.7.2/src/impl/util.js), [Luxon API](https://moment.github.io/luxon/api-docs/index.html) and [pinned declarations](https://unpkg.com/@types/luxon@3.7.6/src/datetime.d.ts) verify fromISO/fromJSDate/fromMillis, setZone, isValid, weekday, startOf, plus, diff, toUTC/toISO/toISODate/toJSDate. Use plus with exact integer milliseconds and integer residuals, not fractional hours or diff('hours') arithmetic. The library accepts wider years/ISO precision than this contract; it does not replace validation. Installation/typings/build remain implementation evidence.

## Accepted counted-hour extension precision

- **Decision**: Follow the 2026-10-02 clarification: positive plain decimal-hour strings, fractions accepted only when the exact duration converts to integer milliseconds. Preserve leading/trailing zero spelling; use the shared browser-safe validation/conversion owner in the existing proposed financial.schema.ts. A linear scan normalizes a scratch representation only, bounded to eight integer/seven fractional digits (16 characters including dot), before any BigInt or power-of-ten conversion. Require exact divisibility of coefficient * 3,600,000 by 10^scale, positivity and a safe integer-millisecond duration bound before Number conversion for Luxon. Validate supported input, intermediate and resulting calendar instants during the calendar calculation. No rounding, truncation or invented minimum.
- **Rationale**: Supported years 0001-9999 span less than 100,000,000 elapsed hours. After removing trailing zeros, an exactly representable finite decimal duration cannot need more than seven fractional digits because 3,600,000 = 2^7 * 3^2 * 5^5. The normalized bound preserves all representable durations without forbidding redundant raw zero spellings or constructing unbounded BigInt. Count residuals in integer milliseconds across Baghdad weekday boundaries, adding to the existing deadline.
- **Alternatives considered**: Whole hours would reject the accepted fractional policy; upward rounding changes the requested duration; floating-point hours may introduce precision drift; an arbitrary raw length/canonical spelling restriction rejects allowed redundant zeros. Later HTTP payload limits remain owned by later endpoints.
- **Evidence**: Spec FR-031/FR-033/SC-005 and [financial boundary](contracts/financial-boundary.md#counted-hour-extension-precision). Exact checks: 1.5 and 0001.5000 -> 5,400,000 ms; 0.0000025 -> 9 ms; 0.0000001 -> 0.36 ms and 0.000001 -> 3.6 ms, both rejected. The maximum normalized duration is below 360,000,000,000,000 ms, safely below Number.MAX_SAFE_INTEGER; result-year validation is still required. Initial 72 counted hours, Friday/weekend rules and independent new-dispatch normalization are unchanged.

## Small immutable source ledger

- **Decision**: Six focused models: Wallet, FinancialOperation, RequestIdentity, LedgerPosting, ReservationAllocation, AuditRecord. Four wallet components, derived total. Postings distinguish source, detailed origin and available/reserved deltas. SQL enforces named bounds/FKs/uniqueness and immutable history.
- **Rationale**: Retains original provenance and explains ownership-preserving reservations without a chart of accounts, redundant totals or reporting platform.
- **Alternatives considered**: One balance loses sources; full history reconstruction on every mutation adds cost; outboxes, event engines, generic repositories and policy-version tables add no P01 capability.
- **Evidence**: Prisma schema currently User/RefreshToken; auth migration contains SQL checks absent from Prisma declarations. [PostgreSQL 18 triggers](https://www.postgresql.org/docs/18/sql-createtrigger.html) supports UPDATE/DELETE and separate statement-level TRUNCATE guards. Guards do not protect against a database superuser; deployment permissions/recovery remain later work.

## One transaction and domain seam

- **Decision**: `modules/ledger/` owns Serializable interactive transactions, parameterized row locks in deterministic order, transaction-bound primitives and safe errors. Trusted authorization/dependent-write callbacks share the same transaction and perform no external I/O. At most three attempts for recognized serialization/deadlock failures.
- **Rationale**: FR-016 requires business changes and financial effects in one commit. Domain callbacks allow current eligibility/state checks without implementing future business workflows.
- **Alternatives considered**: Queue/global locks cannot enforce persisted correctness across processes. Root-client fallback/nested transactions split atomicity. Blanket retries risk duplicate effects.
- **Evidence**: `createDatabaseClient(connectionString)` uses PrismaPg; installed v7 declaration has callback `maxWait`, `timeout`, `isolationLevel`. [Prisma 7 transactions](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions), [v7 raw queries](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/raw-queries), [PostgreSQL 18 locking](https://www.postgresql.org/docs/18/explicit-locking.html). Unversioned Prisma guidance currently describes a different major. Recognize P2034; classify raw/adapter SQLSTATE 40001/40P01 only after installed-adapter tests confirm structured error shape, never broad P2010/message substrings.

## Independent business and request identities

- **Decision**: Unique business `(kind, namespace, key)` binds canonical consequential intent. Optional request `(actorScope, kind, key)` aliases reference the operation/hash independently. Hash an explicit ordered canonical representation; exclude request key, observed clock and changing current eligibility. Save immutable accepted snapshots/outcome.
- **Rationale**: New/absent keys cannot duplicate one event. A new supplied replay key must become bound so later changed use conflicts. Reauthorize visibility and skip mutation callbacks/audit on replay.
- **Alternatives considered**: A single optional key on the operation cannot bind aliases; global keys collide/leak across actors; generic P2002 recovery cannot identify a safe duplicate.
- **Evidence**: Existing SHA-256 helper in `infrastructure/security/token-hasher.ts`; current Prisma error mapper gives generic conflicts, not durable replay logic. Exact conflict recovery happens after the failed transaction, with current authorized lookup.

## Original-source release and consistent reconciliation

- **Decision**: Preserve ACTIVE -> RELEASED allocations and original-source safe release. Add typed immutable walletBefore and kind-specific source/direction/eligible-source/allocation evidence inside existing acceptedTerms JSON, with no new model or public projection. Reconciliation starts a Prisma RepeatableRead callback with static SET TRANSACTION READ ONLY before observation/data reads. In one authorized snapshot scan every wallet operation, including those with no postings, validate each kind's complete expected source posting map/magnitude/origin, before-plus-deltas/outcome, matching audit and reservation/opening/release links, then compare numeric/text ledger/projection/ACTIVE-allocation aggregates. Exclude mutable before-balances/grants from intent hashing and retain original snapshots on replay.
- **Rationale**: CHK035 requires operation amounts and complete posting sets, not just aggregate agreement. A declared credit of 10 with posting/projection 9, or two declared credits of 10 posting 9/11, exposes the difference. The narrow existing JSON snapshot supplies source-order and before/after evidence without guessing timestamp commit order. One read-only snapshot prevents raced false mismatches, while numeric/text preserves cumulative sums beyond bigint. Original reserve outcomes remain ACTIVE after a later release; compare historical outcome to its original allocation rather than current allocation status.
- **Alternatives considered**: Aggregate-only checks hide per-operation faults; starting from postings misses a no-posting operation. Timestamp sorting cannot prove commit order, and current eligibility cannot reinterpret a saved grant. New sequence models/accounting platforms and automatic repairs add no P01 need. Fault fixtures use direct INSERTs allowed by row guards rather than disabling immutability protections. Payout consumption/settlement remains P11.
- **Evidence**: Spec FR-009/FR-025/SC-007, engineering/data-patterns.md operation-amount rule and [internal reconciliation contract](contracts/ledger-service.md#reconciliation-errors-and-diagnostics). Installed Prisma runtime/client.d.ts exposes isolation/maxWait/timeout and parameterized raw queries, not a readOnly option. [PostgreSQL 18 transaction modes](https://www.postgresql.org/docs/18/sql-set-transaction.html), [isolation](https://www.postgresql.org/docs/18/transaction-iso.html), [aggregate types](https://www.postgresql.org/docs/18/functions-aggregate.html) and [Prisma 7 raw queries](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/raw-queries) support this design: sum(bigint) returns numeric, converted to validated integer text for exact BigInt comparison.

## Real migrations and fixture ownership

- **Decision**: Extend current exact schema/table inventories and auth assertions; add fresh/populated-legacy/repeated-deploy financial checks using existing Vitest/Testcontainers. Narrow two API auth suites' global deletion to owned auth fixture users/refresh rows; retain finance histories until container destruction.
- **Rationale**: API files share a container with `isolate:false`; all-user cleanup would conflict with financial Restrict FKs. A new-only migrated DB cannot demonstrate a populated upgrade. Independent clients/barriers, not one transaction's Promise.all, establish races.
- **Alternatives considered**: Deleting finance rows/disabling guards weakens the tested invariant; another runner/Redis is unnecessary. Per-case containers are unnecessary where owned fixture cleanup suffices.
- **Evidence**: Both integration configs/global setups, API app/auth integration cleanup, database inventory/migration tests. Global setup deploys every current migration; populated-upgrade test must separately begin with only the legacy migration applied.

## Authority and safe outputs

- **Decision**: Shared contracts remain browser-safe; actor/process context, eligibility/event evidence and transaction handles stay server-only. Runtime current authority/ownership checks are separate from strict intent schemas. Correction checks active/verified ADMIN with reason/reference. Domain owners decide recipient lifecycle policy; P01 does not universally block earned credits to a suspended recipient.
- **Rationale**: A type/identifier/request key does not authorize mutation or replay disclosure. Replay observation differs from authorizing a new reservation after expiry. No financial route means no invented P01 session subsystem.
- **Alternatives considered**: Client authority, anonymous primitives and blanket owner-active checks either weaken protection or contradict later reward finality.
- **Evidence**: Existing auth middleware reloads account status/role but does not immediately revoke issued access tokens when refresh rows are deleted. P02 owns lifecycle/config hardening. Security-best-practices Express guidance informed trusted context, sanitized driver failures and bounded audit fields; no unrelated security implementation/report is added.
