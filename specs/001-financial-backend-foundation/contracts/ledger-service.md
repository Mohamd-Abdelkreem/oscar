# P01 Internal Ledger Service Contract

**Status**: Proposed server-only interface; not implemented. **Owner**: `apps/api/src/modules/ledger/`. **Wire primitives**: [financial-boundary.md](financial-boundary.md). **Persistence**: [data-model.md](../data-model.md).

No public financial route, arbitrary balance patch, signing adapter, queue or provider verification is added. Future business services supply verified events and current policy through this boundary. A branded TypeScript type is an aid, not runtime authority.

## Trusted context and identities

- Context contains server-derived USER actor UUID or allowlisted PROCESS identity, an injected clock, declared participant wallets and transaction-local authority callbacks. User actors are checked against current relevant account status/role. Recipient ownership/existence is checked separately; do not universally reject an earned credit because its recipient is now suspended.
- A mutation guard checks action authority and required owner/domain state after locks. An observation guard separately authorizes replay/reconciliation visibility. Both are mandatory; intent cannot supply actor role, eligibility, provider confirmation or a safe-release boolean.
- Each FinancialOperation owns exactly one wallet. Unique business identity is `(kind, namespace, businessKey)` with a canonical consequential-intent hash. Namespace is allowlisted by trusted composition; key is nonempty/bounded (1-256 characters) and no secret. Stable identity differs from a generated attempt ID.
- Optional request identity is `(actorScope, kind, requestKey)`; actorScope is derived USER:<uuid> or PROCESS:<allowlisted-id>. Identical textual keys across actors/kinds are independent. Alias binds the operation and canonical intent; source identity still prevents duplicates without a key.
- Canonical hashing uses an explicit ordered field representation: kind, wallet, validated magnitude/source/origin, stable business identity, and action-relevant immutable intent. RELEASE includes its reservation identity; CORRECTION includes credit/debit direction, bounded reason and original-operation reference. Exclude the supplied request key, current clock, mutable wallet balance and changing runtime eligibility. Same identity with changed consequential intent conflicts; accepted terms/state are stored in the original result.

## Entry points and composition

Proposed names describe the target API, not existing symbols:

| Entry point                                                                                                      | Responsibility                                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LedgerService.execute`                                                                                          | Execute one wallet operation, own the transaction/retry, perform current authority/replay checks, and run an optional database-only dependent-domain callback on a new effect. Authorized replay skips that callback. Return a mapped immutable result plus separate replay metadata. |
| `LedgerService.runInTransaction`                                                                                 | Own one Serializable transaction and sorted declared wallet lock set for trusted database-only work. Give the caller the same Prisma.TransactionClient and a transaction-bound ledger handle; no nested transaction/root-client fallback.                                             |
| Transaction-bound `credit`, `debitForPurchase`, `reserveForWithdrawal`, `releaseReservation`, `correctAvailable` | Apply one wallet operation with its own stable business identity and current guard. Reuse the surrounding transaction and create immutable completed result/history/audit.                                                                                                            |
| `LedgerService.recoverOperation`                                                                                 | Authorized identity lookup after lost reply; returns original committed result or safe not-resolved/not-found outcome, never a newly invented effect.                                                                                                                                 |
| `LedgerService.reconcileWallet`                                                                                  | Authorized, scoped, read-only consistent reconciliation; report exact discrepancies without mutation.                                                                                                                                                                                 |

Future purchases/referral awards may affect multiple wallets in one outer transaction, creating distinct per-wallet operations/business keys. Declare/lock the complete set first; undeclared participants fail. The later domain record owns compound request idempotency/outcome and skips its mutations on compound replay. Do not alias one actor/kind/key to several wallet operations or create a P01 batch/result framework. A per-wallet replay returns its original snapshot and does not by itself authorize a second dependent business write.

## Primitive semantics

| Primitive              | Required effect and guard                                                                                                                                                                                                                                                                                                                                 |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Credit                 | Positive exact units; trusted verified event/approval authority and explicit source/origin. Increase that source's available component only. Pending/unverified input is rejected by its owning guard.                                                                                                                                                    |
| Purchase debit         | Positive units; current owning-domain authorization. Consume available referral first, then available non-referral. Insufficient unreserved funds fails all-or-nothing. Never spend reserved funds.                                                                                                                                                       |
| Withdrawal reservation | Positive gross units and transaction-local eligible-source grant. Consume eligible available non-referral first, then eligible referral; Free/expired grants exclude referral. Move to corresponding reserved components, preserving total. Save exact allocation in outcome and accepted grant in acceptedTerms. Fee/net does not reduce gross reserved. |
| Safe release           | Identify existing allocation/wallet; authorize observation first, then on a new release obtain owning-domain proof of safe releasable state in this transaction. Conditional ACTIVE -> RELEASED restores original sources once. No uncertain-reply refund or current-eligibility recalculation.                                                           |
| Correction             | Current active/verified ADMIN, bounded reason (1-500 characters with nonblank content) and original-operation reference. Explicit source, positive magnitude and credit/debit direction; available funds only. Append a new audited operation. No relabeling, reserved debit, reward reversal or fabricated receipt.                                      |

Corrections reference an existing operation on the same wallet and preserve originals. Detailed origins distinguish DEPOSIT, TASK_REWARD, REFERRAL_COMMISSION, PACKAGE_PURCHASE, WITHDRAWAL_RESERVATION, RESERVATION_RELEASE and ADMIN_ADJUSTMENT. DEPOSIT/TASK_REWARD credits use NON_REFERRAL; REFERRAL_COMMISSION credits use REFERRAL. Purchase/reserve/release may affect both sources under their allocation rules; ADMIN_ADJUSTMENT changes one declared source without relabeling another. P01 creates neither actual deposits/tasks/purchases nor payout consumption/settlement methods.

### Accepted evidence for reconciliation

Keep a strict, kind-specific snapshot in the existing `acceptedTerms` JSON; no new column, model or public output is needed. Every operation saves `walletBefore`, with the same four canonical source/state amounts and exact derived total as `walletComponentsSchema`, captured after locks and before its new effect. CREDIT saves its explicit `source`; CORRECTION saves `source`, CREDIT/DEBIT `direction`, bounded `reason` and same-wallet `referenceOperationId`. RESERVE saves its `reservationId` and the trusted `eligibleSources` grant actually used, a unique set of supported fund-source values; RELEASE saves that original `reservationId`. The immutable outcome already saves `walletAfter` and, for RESERVE/RELEASE, the original allocation and accepted result state.

Before-balances and current eligibility grants are server-observed acceptance evidence, excluded from the consequential-intent hash along with clock/request-key/current-balance observations. Declared source, correction direction/reason/reference and release reservation identity remain consequential intent. Do not recalculate original snapshots during replay. These local snapshots support consistency checks; they are not independent proof of an external event, historical eligibility or custody safety.

## Transaction protocol

1. Validate strict intent and required trusted context before beginning; canonicalize/fingerprint stable intent. Derive authority independently of submitted owner IDs.
2. Begin Prisma 7 interactive Serializable transaction (initial maxWait 5s, timeout 10s). Lock relevant actor/authority accounts deterministically, then sorted wallet IDs, then reservation rows; all callers join the same ordering. Recheck relevant current authority and safe visibility before identity results can be disclosed.
3. Inspect request binding and business identity. Exact authorized committed replay returns original outcome and bypasses financial/domain mutations. Different intent produces conflict. An identical replay under a new supplied key inserts only that alias; no successful mutation audit repeats.
4. For a new effect, establish mutation/domain state authority, compute bounded deltas/allocation/after-snapshot in memory. Insert the completed immutable operation, then its postings/projection/allocation, dependent domain writes and required audit using this same transaction client. A later callback failure rolls everything back.
5. Commit before returning success. There is no persistent started/pending operation; uncommitted data is invisible. A lost response does not prove failure or safe release. Recover using existing identity.

At most three complete transaction attempts on P2034. Exact structured 40001/40P01 raw/adapter classification may be added only when real installed-adapter integration tests verify it. No broad P2010/P2002 catch, message matching, funds/authority/payload retry or external I/O inside retryable callbacks. Retry retains identities and rechecks relevant state; exhaustion returns safe unresolved conflict, not success.

For standalone `execute`/`recoverOperation`, a known business/request unique-constraint failure leaves the aborted transaction, then reads that exact identity in a fresh authorized context, compares fingerprint/target and recovers only an identical committed result. If no authorized matching result exists, return safe conflict/not-resolved; do not blanket-retry or disclose another operation. Bind any new alias through its own safe transactional uniqueness check. A transaction-bound primitive instead propagates the conflict to abort the outer transaction; only the owning domain can recover a compound result. One recovered per-wallet effect cannot imply compound success after dependent domain writes have rolled back.

## Replay and release outcomes

Same request or business identity, same intent and current visibility: original result, no new money/postings/domain writes/mutation audit. Same textual key in another scope neither retrieves nor conflicts merely by text. Changed amount/wallet/source/reference conflicts without mutation. Authority denial returns no amount/allocation/result/existence detail.

Release replay of the same identity observes its original RELEASED result. Another release identity against a closed allocation returns a safe already-closed conflict, with no second financial effect. An ACTIVE reservation lacking same-transaction safety evidence stays reserved. P10/P11 must implement their actual unsent/in-flight guard and consumption transitions before exposing withdrawal APIs.

## Reconciliation, errors and diagnostics

Use one scoped Prisma RepeatableRead transaction. Its first statement inside the callback is the fixed `SET TRANSACTION READ ONLY`, before observation-authority or wallet reads; Prisma transaction options do not provide a `readOnly` flag. Its observation guard performs reads only. Authorize observation and perform all checks in this one snapshot. Aggregate source/state deltas and ACTIVE allocations as PostgreSQL numeric/text, parse exact integers, and compare with all four wallet components. Do not cast cumulative sums to bounded bigint or Number. No repair.

Begin the per-operation scan from every FinancialOperation for the authorized wallet, with a LEFT JOIN to postings; starting from postings would hide an operation with no postings. Load its original terms/outcome, linked allocation and required audit from this same snapshot. Require exactly the complete expected source posting set below: one posting for each nonzero expected source effect, no missing or extra source, and exact deltas. All comparisons use exact units; database uniqueness and individual row shape do not prove a complete operation.

| Kind           | Complete posting and saved-evidence checks                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CREDIT         | Exactly one posting in the accepted `source`, with available delta equal to positive `magnitudeUnits` and reserved delta zero. P01 CREDIT accepts only DEPOSIT/TASK_REWARD with NON_REFERRAL or REFERRAL_COMMISSION with REFERRAL. ADMIN_ADJUSTMENT belongs to CORRECTION in this phase; P08 owns any separately audited manual-credit contract/guard extension.                                                           |
| PURCHASE_DEBIT | PACKAGE_PURCHASE origin; negative available-only postings whose magnitudes sum exactly to `magnitudeUnits`. Compute expected referral debit as the lesser of magnitude and recorded before-available referral, then take the remainder from before-available non-referral; reject insufficient before-funds or a different source split. Every reserved component remains unchanged.                                       |
| RESERVE        | WITHDRAWAL_RESERVATION origin; exactly one linked original allocation whose wallet/opening operation/reservation ID/gross match this operation. Compute the non-referral-first split from `walletBefore` and the accepted eligible-source grant, excluding reserved and ineligible funds. Each nonzero original source amount has equal negative available/positive reserved deltas; their sum equals gross and magnitude. |
| RELEASE        | RESERVATION_RELEASE origin; exactly one original allocation links its release operation to this same wallet/accepted reservation ID. Its current state is RELEASED with release fields present. Magnitude equals original gross; postings are the exact source-by-source inverse of that allocation, never a split from current eligibility or balances.                                                                   |
| CORRECTION     | ADMIN_ADJUSTMENT origin; exactly one posting in the accepted source, with positive/negative available delta equal to magnitude according to CREDIT/DEBIT direction and reserved delta zero. Required reason and same-wallet original reference agree with its required audit. No source relabeling or reserved-fund debit.                                                                                                 |

For every operation, runtime-validate the original snapshot/result shapes and match outcome operation ID, wallet ID, kind, amount and normalized recorded time to the immutable operation. Adding that operation's exact posting deltas to `walletBefore` must yield all four saved `walletAfter` components and total without underflow/overflow. Every RESERVE/RELEASE outcome must carry the identical original reservation ID/allocation; RESERVE's recorded result remains ACTIVE even when the allocation has since been safely RELEASED, while RELEASE's recorded result is RELEASED. An ACTIVE allocation has no release link/time; a RELEASED allocation has one matching release operation, and every opening/release operation has its expected allocation. Require one matching mutation audit per operation, including trusted actor/action and correction reason/reference. Return discrepancies for malformed/missing evidence rather than coercing defaults or rewriting history.

These checks establish consistency with locally recorded before-balances and grants. Do not infer a commit sequence from createdAt/UUID order, compare an old walletAfter with today's wallet, reinterpret historical eligibility, or claim the snapshots independently prove provider approval. Current projection and allocation aggregate checks remain necessary alongside the per-operation checks. P11 consumption/settlement and external-event verification remain excluded.

Return safe categorized discrepancies identifying the authorized wallet and, where relevant, operation/allocation ID, source/component and exact expected/actual values. Monetary comparisons/differences use canonical signed decimal strings; counts/states use their declared non-money types. A cumulative aggregate or diagnostic difference may exceed the single-movement storage bound: do not clamp it, convert through Number, or apply the bounded posting-delta schema to that diagnostic. Persisted component/movement bounds remain unchanged. Categories distinguish missing/extra postings, magnitude/source mismatch, invalid allocation/link/state, invalid saved outcome, missing/mismatched audit and projection mismatch. Do not return entire acceptedTerms/outcome/audit blobs, hashes, raw driver data or another wallet's evidence. A clean aggregate does not suppress an operation discrepancy.

Proposed stable safe module codes: FINANCIAL_INVALID_INPUT, FINANCIAL_AUTHORITY_DENIED, FINANCIAL_INTENT_CONFLICT, FINANCIAL_INSUFFICIENT_FUNDS, FINANCIAL_BOUNDS_EXCEEDED, FINANCIAL_RESERVATION_CLOSED, FINANCIAL_RESERVATION_UNSAFE, FINANCIAL_RETRY_EXHAUSTED and FINANCIAL_INTEGRITY_ERROR. Use the existing AppError shape where appropriate; no P01 HTTP statuses/routes are invented. Preserve existing auth error mapping; translate financial named constraints narrowly and sanitize unknown driver failures before ordinary logging.

Allowlisted diagnostics contain operation/wallet/request correlation identifiers where authorized, safe code and attempt count. Never raw commands, hashes, outcome JSON, tokens, secrets, database connection strings/driver metadata or private provider/signing payloads. Audit records are bounded trusted action/actor/time/reason/reference, atomically written once per new effect. Operational denial/retry logs are distinct from successful mutation audit. Accepted single-admin/no-2FA risk and current auth session limitations remain later gates, not security guarantees.

**Future acceptance**: real PostgreSQL service/concurrency/reconciliation tests listed in [plan.md](../plan.md), including unauthorized replay, authority/write races, safe unknown driver-error projections, identity aliases, multi-write rollback and original-source release. No such implementation/test run is claimed by this contract.

Reconciliation acceptance includes valid sequences of every P01 kind and original RESERVE outcomes after release, plus controlled faults in an isolated migrated database: a complete CREDIT record/audit with no postings and unchanged projection; a CREDIT declaring 10 USDT with a valid positive-only 9 USDT posting and matching 9 USDT projection; and two declared 10 USDT credits posting 9/11 USDT whose total projections and aggregate command magnitudes agree. Also exercise a well-shaped but inconsistent saved outcome and a missing required audit. Seed these faults using direct INSERT of new fixture-owned operation/posting/audit rows and bounded wallet projections, not by asking the production service to create invalid history. The faults retain valid individual bounds, FKs, uniqueness, actor/origin and posting shapes; completeness is deliberately the service/reconciliation responsibility. Never disable UPDATE/DELETE/TRUNCATE guards or modify historic rows. If a planned insert guard already rejects a fault, assert that actual constraint result and choose a fault that remains admissible; do not weaken the guard. Reconciliation must report each surviving fault, leave all fixture rows unchanged and never mistake aggregate agreement for success.
