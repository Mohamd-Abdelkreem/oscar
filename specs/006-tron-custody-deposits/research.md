# P06 Research Decisions

**Date**: 2026-10-06 | **Scope**: P06 only | **Status**: design decisions resolved; implementation and operational acceptance unexecuted.

Authority: [clarified spec](spec.md), [roadmap](../../PLAN.md), constitution 1.0.0 and all eight engineering guides. Repository facts were inspected locally; upstream behavior was checked against official documentation/source. Proposed owners below do not exist yet unless explicitly described as existing.

## R1. Preserve the existing runtime and add one provider dependency

- **Decision**: Keep Node 24, pnpm 11.17.0, TypeScript 5.9.3, Express 5.2.1, Prisma/adapter 7.9.1, PostgreSQL 18.4, Zod 4.4.3 and Vitest 4.1.10. Propose API-only `tronweb` pinned to **6.5.1**, with its bundled types. Use its named ESM export inside protected adapters. Add `worker.ts` and `signer.ts` to the existing API build; use PostgreSQL polling for P06. No Redis/BullMQ or new workspace package is needed here.
- **Rationale**: API `type: module` and NodeNext build already cover `src/**/*.ts`. TronWeb 6.5.1 publishes ESM and type declarations; it has no declared Node engines constraint. This is a compatibility candidate, not a tested integration: implementation must prove import/build, exact amount handling and signing on Node 24.18.1 before acceptance. Existing API scripts currently start only HTTP.
- **Alternatives considered**: New signer microservice/package, another runner and queue infrastructure add boundaries without an existing build requirement. Direct provider access remains mandatory; a custodial payment provider is excluded.
- **Evidence**: `apps/api/package.json`, `apps/api/tsconfig.json`, `apps/api/tsconfig.build.json`, `pnpm-lock.yaml`; [6.5.1 release](https://github.com/tronprotocol/tronweb/releases/tag/v6.5.1), [versioned package manifest](https://raw.githubusercontent.com/tronprotocol/tronweb/v6.5.1/package.json).

## R2. Discovery is a hint; solidified receipts authorize credit

- **Decision**: Pin an explicit network identifier and expected genesis block identity, provider host, token contract and six token decimals. Verify the provider network at startup and on reconnect. Use TronGrid account TRC-20 history for candidate TxIDs. Obtain transaction and transaction-info through the configured `/walletsolidity/gettransactionbyid` and `/walletsolidity/gettransactioninfobyid` boundary. Require matching TxID, successful smart-contract execution, solidified inclusion and agreeing canonical block identity; contradictory/missing evidence remains unresolved. Decode the complete raw receipt `log[]` locally.
- **Rationale**: Indexer `only_confirmed`, token symbol, explorer data and broadcast acknowledgement cannot replace the confirmed receipt. Match the exact allowlisted emitting contract, Transfer topic/ABI shape, 20-byte decoded recipient and positive uint256 amount. Decode bytes to `bigint`; reject amounts or resulting wallet ownership above 9223372036854775807 micro-USDT. Network is not inferred from a Base58 address. Untrusted response shape/size is validated before use.
- **Alternatives considered**: User TxID ownership claims, trusting indexer amounts/event indices, elapsed-time confirmation waits and symbol checks do not establish ownership/finality.
- **Evidence**: [exchange wallet integration](https://developers.tron.network/docs/exchangewallet-integrate-with-the-tron-network), [solidified transaction info](https://developers.tron.network/reference/gettransactioninfobyid-1), [account TRC-20 discovery](https://developers.tron.network/reference/get-trc20-transaction-info-by-account-address).

## R3. Use raw log position and durable complete replay

- **Decision**: Event identity is `(configuredNetwork, txId, logIndex)`, where `logIndex` is the zero-based position in the unfiltered canonical receipt log array. Verify every eligible log, including several in one transaction. Persist a transaction candidate before scan progress moves. Each address has bounded hot windows, a durable pending queue and a recurring historical replay cycle back to its provisioning boundary. A finite recent overlap is insufficient by itself.
- **Rationale**: Indexed observations can be delayed/out of order. Capture a conservative solidified chain block/timestamp boundary before generating the address, retain it in assignment/recovery records and use its inclusive timestamp for historical replay; host-clock provisioning time is not a safe cutoff. Store fixed inclusive window bounds, query policy and fingerprint together; pagination must preserve other parameters. Inclusive overlapping boundaries and deduplication avoid losing equal-timestamp events. Invalid/expired fingerprints restart the same window. Atomically persist candidate IDs and the next checkpoint before acknowledging a page. Verification/financial commit happen separately; pending work survives finished windows and history replay recurs.
- **Alternatives considered**: An in-memory cursor, one high-water timestamp or a limited overlap without historical replay cannot meet FR-019. Full-chain node operation is outside the MVP. Provider retention/completeness must support the selected history boundary; missing coverage blocks acceptance rather than becoming a guessed empty interval.
- **Evidence**: [TronGrid pagination contract](https://developers.tron.network/reference/get-trc20-transaction-info-by-account-address), [custodial integration guidance](https://developers.tron.network/re/docs/track-1-exchange-and-custodial-wallet-integration).

## R4. Reuse the actual ledger, including its replay boundary

- **Decision**: Use existing `LedgerService.execute`/`runInTransaction`, exact money helpers and transaction-client domain writes. Deposit namespace is proposed `p06.deposit`; business key is network/TxID/raw-log-index. Credit as existing `CREDIT` + `DEPOSIT` + `NON_REFERRAL`, under allowed process `deposit-indexer`. Create immutable receipt, credit, projections and audit in one transaction. Compare existing receipt evidence in the observation guard before returning a ledger replay.
- **Rationale**: `ledger.service.ts` returns replays before invoking `domainWrite`. A replay cannot create a missing receipt or silently accept conflicting token/recipient/amount evidence. Existing sorted account/wallet/reservation locks and Serializable transactions allow at most three recognized conflict attempts. Unclassified uniqueness errors are not proof of successful deposit processing. Process credit does not require an active wallet owner, so bans/expiry retain inbound attribution without granting access.
- **Alternatives considered**: A separate balance writer, mocked financial atomicity and repair by synthesizing a historic receipt violate source integrity.
- **Evidence**: `apps/api/src/modules/ledger/{ledger.service.ts,ledger.transaction.ts,ledger.types.ts,ledger.effects.ts}`, existing P01/P04/P05 financial migration SQL and tests.

## R5. Initial manual grants retain compatible financial wire kinds

- **Decision**: Extend protected ledger credit intent/effects for `CREDIT` + existing `ADMIN_ADJUSTMENT` origin, fixed `NON_REFERRAL`; do not add a public financial kind. Add a `ManualCredit` record with required durable UUID `actionId`, target, original ADMIN actor, amount, reason, confirmation and discriminated external/same-wallet-operation reference. Bind all consequential fields into the fingerprint and persisted outcome. Use `p06.manual-credit` plus globally unique actionId as business identity, separately from actor-scoped request keys.
- **Rationale**: Clarified C1 explicitly allows first/new grants. Existing `CORRECTION` requires a prior same-wallet operation and remains unchanged. SQL guards need a forward extension for ADMIN grant authority/reason/reference alternatives. Ledger writes audit before its domain callback, so grant/audit/ManualCredit cross-row validation is deferred until transaction end; immediate actor/action/basic checks remain. Retain existing strict historical CREDIT snapshots; new grant metadata is mandatory for new administrative credits. Existing wallet/finance schemas continue to expose CREDIT/ADMIN_ADJUSTMENT with `correction=null` for grants. No P06 web edit is necessary.
- **Replay**: Same actionId and original actor/payload with another request key returns the stored result. Same request key for changed action/payload, or same actionId with another actor/target/amount/reason/reference, conflicts. External reference is not chain proof or inherently a globally unique invoice; different UUIDs represent different explicit grants. P07 must preserve the actionId while observing/retrying one intent, and must not silently generate a replacement after a lost reply. Missing actionId is rejected.
- **Alternatives considered**: Fake preceding ledger operations, REFERRAL-selectable grants, arbitrary balance patches and a new shared financial kind would introduce incorrect semantics or unnecessary client changes.
- **Evidence**: P06 C1/FR-023-025; `ledger.types.ts`, `ledger.effects.ts`, `ledger.service.ts`; `packages/contracts/src/{financial/financial.schema.ts,wallet/wallet.schema.ts}`; `apps/api/src/modules/wallets/wallets.mapper.ts` and existing wallet queries.

## R6. Independent encrypted key records precede address publication

- **Decision**: Generate independent TronWeb accounts only in the signer. Persist an assignment-bound AES-256-GCM envelope locally before external I/O: random 12-byte nonce, 32-byte protected encryption key, 16-byte tag, format/key version and authenticated employee/assignment/address/network context. Keep signer-only files outside source/public/proof roots. Derive the public address again after decryption. Preserve unpublished generated records and reconcile them by stable assignment ID.
- **Rationale**: One worker claims each durable provisioning record; unique employee/network and network/address constraints plus stable encrypted envelopes recover concurrency/lost replies. Off-host acknowledgement and matching database binding precede READY publication. Generation, recovery readiness, activation and resources remain separate. A token arriving at an inactive address may qualify for credit, while its sweep waits for activation/resources. Rotation adds acknowledged envelopes under a new key ID; it never destroys access to existing published keys.
- **Alternatives considered**: Public/API key generation, employee-controlled keys, address reuse, unacknowledged nightly backup and storing keys with browser-facing persistence are excluded.
- **Evidence**: [Node 24 authenticated encryption](https://nodejs.org/docs/latest-v24.x/api/crypto.html), [TRON account semantics](https://developers.tron.network/docs/account), [account generation](https://tronweb.network/docu/docs/API%20List/utils/createAccount/).

## R7. A fixed one-shot SSH helper provides durable off-host acknowledgement

- **Decision**: Use operator-provisioned OpenSSH and a forced-command, one-shot helper from the same API build, proposed `infrastructure/custody/recovery-store.cli.ts`, on an independent Linux recovery host. It accepts bounded PUT/GET/LIST ciphertext messages over stdin. It validates fixed IDs/digests, writes exclusively, fsyncs the file, publishes without replacement, fsyncs the directory and reads back before acknowledging. Same object/same digest is idempotent; different bytes conflict. Bounded inventory enumeration discovers records missing from an older DB backup.
- **Rationale**: This is a protected recovery tool, without an extra running service or npm dependency. Local adapter uses fixed executable/argument arrays with no shell, pinned host key, BatchMode, no forwarding and protected SSH configuration/identity files. Credentials and ciphertext never become command-line values/logs. Ordinary SFTP upload/readback alone does not prove durable directory publication. Independent storage/retention and separately escrowed decryption authority remain operator prerequisites. A local fake remote directory tests the storage logic but does not prove off-host acceptance.
- **Alternatives considered**: A new generic backup platform, arbitrary object URLs and stock SFTP acknowledgements are unnecessary or insufficient for the required publication guarantee.
- **Evidence**: [OpenSSH SFTP manual](https://man.openbsd.org/sftp), [protocol extensions](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL), [server fsync implementation](https://github.com/openssh/openssh-portable/blob/master/sftp-server.c), [Node 24 file sync](https://nodejs.org/docs/latest-v24.x/api/fs.html).

## R8. Fixed treasury sweeps use one safely reconciled signed attempt

- **Decision**: A protected operator CLI records an immutable fixed-treasury intent, under a nonpublic process/database identity. Signer independently rechecks source ownership, configured network/token/treasury, exact amount, fresh funds/resources and limits. Build, sign, persist the returned signed transaction and TxID in encrypted protected storage, acknowledge off-host recovery, then durably record broadcast intent before calling `sendRawTransaction`. Do not use `.transfer(...).send()`.
- **Rationale**: TronWeb 6.5.1 signing returns a new signed object. Persist that return value together with the complete immutable intent/policy/operator/claim snapshot in its encrypted recovery object. If the DB attempt lacks signed metadata after a crash, inspect the stable local/off-host envelope before any rebuild/sign; an attempt ID alone does not preserve bytes. One active source intent prevents competing spends. Lost acknowledgement stays UNKNOWN; rebroadcast identical bytes only within original validity/policy. Automatic replacement is disabled: expired/not-found remains unresolved until authoritative nonexecution and complete solidified coverage beyond expiration are established. Provider outage or one empty lookup is insufficient.
- **Finality**: Verify canonical successful receipt and exact intended token movement to treasury, then record source/treasury movement and company costs; no wallet operation is performed. Snapshot energy fee limit separately from activation, bandwidth and other fees; `fee_limit` is not total-cost protection. Read current chain resource parameters rather than hardcoding TRX tariffs. Operator funding is capped/manual; no automatic top-ups or energy trading.
- **Evidence**: [transaction lifecycle](https://developers.tron.network/docs/api-signature-and-broadcast-flow), [signing API](https://tronweb.network/docu/docs/API%20List/trx/sign/), [broadcast API](https://tronweb.network/docu/docs/API%20List/trx/sendRawTransaction/), [resource costs](https://developers.tron.network/docs/paying-for-resources).

## R9. Restoration has a shared mutation fence and separate dispatch pause

- **Decision**: Add a durable financial-runtime control row and mutation admission in existing ledger transactions. Mutations take a shared transaction advisory lock and locked control-row read before existing authority/wallet locks. Restore takes the exclusive advisory lock, drains active mutations and fences new financial writes. Serializable admission must use a locked read, so a pre-wait snapshot cannot bypass a newly committed fence. Read/reconciliation observations remain allowed. Signer dispatch uses the same fence and a separate new-dispatch pause at its durable broadcast-intent admission point.
- **Rationale**: HTTP middleware or an in-memory pause cannot protect competing services. No DB transaction spans SSH, signing or chain I/O. Already admitted broadcast intent remains possibly sent/reconcilable. Each runtime starts with a fresh in-memory boot UUID and FinancialRuntimeAdmission request; mutations stay closed until protected tooling acknowledges that UUID/current control generation after inventory/history/attempt validation. Runtime roles cannot acknowledge their own request. Restore advances generation, invalidating old boots; a restored OPEN row cannot authorize a new process. P06 proves actual startup/drain/fence/recovery; P11 proves deployed WAL/PITR/full-system admission.
- **Alternatives considered**: Queue locks, pausing only the indexer, and chain rescans reconstructing off-chain purchases/rewards/grants cannot satisfy recovery.
- **Evidence**: Existing `ledger.transaction.ts`; [PostgreSQL 18 locking](https://www.postgresql.org/docs/18/explicit-locking.html); roadmap Section 5.6/FR-033.

**P06 analysis correction (2026-10-06)**: Current `LedgerService.recoverOperation` calls `replay`/`bindAlias`, so its observation path can insert RequestIdentity. P06 deliberately changes recovery to read-only for every caller, retaining existing alias/payload/authority/evidence checks without binding a fresh key. Alias-changing replay remains admitted `execute`/`runInTransaction` work. T012/T014/T042 own the change and closed-boot/fenced/new-key/admitted-replay evidence; no source implementation or test execution follows this design correction. The [runtime operational policy](contracts/custody-runtime.md#operational-signals-and-operator-ownership) also supplies the previously missing basic signal triggers, bounded thresholds and operator ownership; actual operational configuration remains an acceptance input.

## Resolved unknowns and remaining acceptance inputs

All technical unknowns considered by this planning run have decisions above. No unresolved technical clarification remains. Required operational values are explicit inputs rather than invented facts: designated test network/token/genesis, provider access and historical coverage, fresh test-only funding keys/recipients, fixed company treasury, resource/scan limits, independent recovery host/retention/owner, separately protected decryption recovery and Linux isolation environment. None was provisioned or verified by PLAN. Missing inputs prevent controlled execution and leave P06/P07 gate incomplete. Existing no-2FA/single-admin and compromised-host risks remain; deployment, real funds and release are separately authorized.
