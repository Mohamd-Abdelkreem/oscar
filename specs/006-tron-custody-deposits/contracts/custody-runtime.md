# P06 Protected Runtime Contract

**Status**: proposed private process/tool/storage protocol. It is not an HTTP signing API and is not implemented by PLAN. Ownership: existing API build with proposed `worker.ts`, `signer.ts`, custody/treasury modules and protected infrastructure adapters. See [data model](../data-model.md) and [research](../research.md).

## Process authority and configuration

| Process                        | Allowed authority                                                                                                           | Explicit denial                                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Public API                     | Current authenticated employee requests/reads; ADMIN grant/history; ordinary owning financial service                       | No keys/decryption/signing/treasury dispatch or recovery-host credential/mount.                          |
| Deposit worker                 | Configured provider reads, durable scans/candidates, verified receipt credit through ledger, public-metadata reconciliation | No private keys/signed material/treasury intent creation or arbitrary process identity supplied by jobs. |
| Private signer                 | Claim durable provisioning/sweep intents, private key recovery, independently allowed signing/broadcast/reconciliation      | No public listener, arbitrary destination/raw-signing/key-export request or import from app/router.      |
| Treasury/recovery operator CLI | Authenticated protected OS/database identity, fixed treasury intent, status/pause and gated recovery operations             | Browser ADMIN credential alone is insufficient; no arbitrary key/destination/command/path argument.      |
| Independent recovery helper    | Fixed bounded PUT/GET/LIST immutable encrypted objects under private root                                                   | No general shell, overwrite/delete, user-selected storage paths or plaintext key output.                 |

Use process-specific injected `DATABASE_URL` values with nonowner roles. Public API/worker cannot alter sealed attempt/key/recovery authority. Migrator owns forward schema; protected runtime-role grants are separate from public credentials. Prove privileges in isolated tests. Existing monorepo source/output may contain signer **code**, but no custody secret/private runtime file is embedded in browser or shared contracts; executable permission/mount/credential tests prove actual isolation.

API, worker and signer startup require their own effective `p06_api`, `p06_deposit_worker` or `p06_signer` membership before boot registration or accepting traffic/work. Recovery membership, other runtime memberships, direct/inherited public schema/relation ownership and superuser/role-management/RLS-bypass privileges or memberships are rejected. The protected recovery CLI retains its separate explicit `p06_recovery_operator` authority; normal runtimes cannot acknowledge their own boot or open admission.

Proposed focused configuration includes explicit `TRON_NETWORK`, `TRON_EXPECTED_GENESIS_BLOCK_ID`, `TRON_PROVIDER_URL`, public `TRON_TOKEN_CONTRACT`, `TRON_TREASURY_ADDRESS`, scan/resource caps and private provider API-key file. Signer-only config includes `CUSTODY_KEY_FILE`, key ID, primary storage root, `CUSTODY_SSH_CONFIG_FILE`, fixed recovery-host alias/root identity and protected operator identity. These names are proposed additions to `.env.example`/runtime parsers, not existing env support. Public parsers see only public network/token/readiness metadata; they never import privileged config barrels. Test keys/config are explicit temporary injected files, with no default mainnet/secret fallback. Production forbids placeholder/missing/shared unsafe values.

Provider host/scheme/redirect policy and expected genesis/network are allowlisted; token decimals must verify as six. Testnet setup permits only designated SHASTA/NILE test configuration with explicit token/provider/genesis/recipients/funding, failing MAINNET/mismatch. Base58 syntax is not network identity. OpenSSH host keys are pinned; BatchMode/IdentitiesOnly/no forwarding/no arbitrary remote commands. Local subprocess uses fixed executable/argument array without shell; no credential/key/ciphertext bytes in argv, logs or ordinary scripts. Keys are loaded from protected files only in the owning process.

## Provisioning operation

Input is the committed assignment ID and allowed operation PROVISION_DEPOSIT_ADDRESS. Both API request creation and signer publication check current runtime/control admission before ownership locks; restore blocks new provisioning/publication against incomplete recovered bindings. Signer rereads owner/network/state/version and conditionally claims. No caller-supplied private/public address becomes an assignment.

Before key generation, persist a conservative solidified chain block/timestamp boundary for inclusive historical replay; host-clock time cannot define the floor. Stable assignment ID owns the key envelope, including complete assignment/employee/wallet/network/address/scan-boundary recovery payload. Persist/fsync locally before external I/O; after crash inspect it rather than generating another key. AAD binds the contents/format/key version. Off-host record must match envelope/context/digest; decrypt and rederive address during recovery. Only matching ACK/durable DB binding enables READY. Output is public readiness/assignment/address only. Missing/tampered recovery leaves nonready/fenced without discarding keys.

## Recovery helper protocol

One authenticated forced SSH command starts the same API build's proposed `recovery-store.cli.ts`. No generic daemon runs. Fixed command receives one bounded JSON message on stdin; object IDs are UUID/type/version identities, not filesystem paths. Maximum envelope/message size is a validated 256 KiB, list page at most 100 with opaque continuation cursor. The helper's fixed private root excludes symlink ancestry/traversal; 0700 owner directory/0600 files and nonowner denial are tested on Linux.

| Operation | Input                                                               | Output/effect                                                                                                                                                                                   |
| --------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PUT       | Object type/ID/version, complete encrypted envelope, SHA-256 digest | Exclusive temp write, file fsync, no-replace publication, directory fsync, verified readback; acknowledge ID/digest only after durability. Same bytes/id is idempotent; changed bytes conflict. |
| GET       | Valid fixed object identity                                         | Authorized bounded encrypted envelope/digest; caller authenticates/decrypts/validates binding. Missing is unavailable, not empty success.                                                       |
| LIST      | Allowed object type, bounded page/cursor                            | Inventory of IDs/digests/versions sufficient to find post-snapshot assignment/attempt records; no keys or arbitrary paths.                                                                      |

ACK contains record identity, digest, protocol version and durable acknowledgement time; authenticated channel and exact readback establish the selected storage contract. It is not accepted before durable storage. Lost ACK repeats GET/PUT of the same object. Private stderr is mapped to safe codes, never copied into diagnostics. Local adapters bound subprocess time, bytes and retries and close/kill owned children on failure. Off-host independence/retention/backup/decryption escrow and actual recovery-host durability remain operational evidence requirements.

Rotation adds new acknowledged encrypted versions for the same key/address; no overwrite of a published historical binding. Recovery compares full current inventory with DB rows, confirms key/assignment and signed-attempt identity, imports only under the fence and retains mismatch as a gate. DB financial history is recovered separately; encrypted key inventory cannot reconstruct purchases/rewards/grants.

An interrupted rotation reuses the protected next-version envelope after validating its key identity and complete original payload. Local publication and lost SSH acknowledgement therefore retry the same ciphertext/digest, retaining old-version readability. Recovery admission's independent digest also covers users, authentication sessions and identity lifecycle audit; missing bans, admin deactivation or session revocation keep the restored database fenced.

## Deposit verification interface

Candidate input: configured network + canonical TxID. Discovery metadata cannot authorize credit. Provider adapter returns validated solidified transaction, transaction-info and block evidence, with bounded calls; it cannot return fake receipt/zero/empty on failure.

Verifier produces either canonical eligible raw-log movements or explicit unavailable/unfinalized/ineligible/conflict. Each movement includes exact configured network/token, sender/assigned recipient, bigint units, raw logIndex and immutable block/execution/finality evidence. Ledger actor is allowlisted process `deposit-indexer`, not a caller-provided actor. No provider call occurs within financial transaction.

Matching receipt and CREDIT/DEPOSIT operation/posting/projection/audit commit together under existing ledger locks/identity. Replayed operation must already have matching receipt/evidence; no repair receipt is fabricated. Candidate financial overflow/failure is retained for retry/investigation and no page checkpoint can erase it. Inbound qualifying credit remains 24/7 despite activation/subscription/account restrictions.

## Treasury tool and durable intent

Proposed `treasury.cli.ts` supports bounded create/status/reconcile/pause operations. Create accepts source assignment UUID, operation UUID, exact positive amount and reason; recipient/network/token come only from validated fixed configuration. CLI flags/names are finalized with the implementation parser, so this plan supplies no unverified executable flag example. Repeated operation identity binds operator/payload; changed intent conflicts. No raw key/signed bytes/custom contract/destination parameter is supported.

Before signing, reread immutable intent/current policy, recovered source and fresh balances/resources. Reject treasury equal to an employee assignment. Enforce one active source/network/token operation in PostgreSQL through all signing/signed/submitted/UNKNOWN states. Snapshot exact amount and independent maximum sweep, Energy fee limit, total estimated company-cost/resource/funding budgets. Failed estimate is unavailable, not zero; `fee_limit` is not total transaction cost. Obtain current chain parameters and keep manual funding/activation separate from USDT ownership.

Signer selection takes at most twenty due sweeps ordered by next attempt time, creation time and ID. A pre-attempt failure retains the immutable intent/source claim, stores a safe failure code and defers retry for five minutes; policy/evidence conflicts emit a protected conflict signal. Independent later sources can progress while rejected intents wait. A restored matching policy can retry the retained intent when due.

Unsigned transaction is independently validated: one TriggerSmartContract token transfer, correct source/contract/transfer ABI recipient+uint256 units, zero TRX/TRC-10 call value, allowed permission/signature policy, bounded expiration/TAPOS/fee fields and SDK-derived raw transaction/TxID agreement. A compromised durable row or SDK response cannot ask the signer to approve/transferFrom/arbitrarily sign.

## Attempt ordering and broadcast semantics

1. Reserve stable attempt ID under source/control admission. On resume inspect its local/off-host signed envelope before any build/sign, even if DB TxID/digest is null; recover it first. Build/sign outside DB transactions only when no prior signed envelope exists and the operation is safely unsent. Persist the **returned** TronWeb 6.5.1 object with complete immutable sweep intent/policy/operator identity/reason/source claim/timestamps and attempt metadata; validate TxID/intent, encrypt/fsync and acknowledge off-host SIGNED_ATTEMPT. IDs/hashes alone cannot restore missing authority. No second signature/transaction follows a lost response.
2. Recheck current fence/pause/policy/intent and durably admit BROADCAST_INTENT, retaining TxID, actual expiration and earliest solidified observation boundary. Acknowledge that immutable recovery record before the first network send. A failure before send resumes the same identity; a possibly sent attempt never becomes safely failed from timeout alone.
3. `sendRawTransaction` response records SUBMITTED or UNKNOWN observation. It does not settle anything. DUP_TRANSACTION_ERROR is not success/nonexecution evidence. Reconcile the same original TxID through solidified canonical evidence.
4. While original validity/current dispatch policy permits, bounded retry may use **identical signed bytes**. Changing expiration/TAPOS/raw data/destination/amount/signature creates another attempt and is prohibited automatically. Dispatch pause prevents new initial/rebroadcast admissions; already admitted work may finish its send after recovery ACK and remains possibly sent/reconcilable. Read-only reconciliation continues. No claim of zero sends after a pause is made.
5. Final success requires canonical-success receipt and intended exact configured-token Transfer from source to fixed treasury. CHAIN_FAILED requires canonical solidified failed execution and verified absence of successful intended movement; retain actual company costs. Neither case changes employee wallet/posting count; chain failure never automatically signs a replacement.
6. Possible submission past expiration remains UNKNOWN unless synchronized solidified coverage beyond expiration and complete relevant history prove original nonexecution. Local clock, outage or one empty lookup does not prove it. Protected audited operator resolution may close EXPIRED_PROVEN_UNSENT only with that evidence; no automatic replacement signer exists in P06. Missing coverage keeps the source active/blocked.

Interrupted signed storage/ACK/DB/broadcast stages recover stable objects and compare digests before acting. Off-host broadcast intent can reveal a post-snapshot attempt missing from DB; recovery restores its metadata/claim before dispatch admission. Unknown cannot release the source or become a new employee credit.

## Runtime control and recovery admission

Financial fence and new-dispatch pause are distinct. Mutating ledger admission uses shared advisory xact lock plus locked control-row read before existing authority/wallet locks; restore's exclusive lock drains active mutations and commits a fence. Serializable read locking/recognized retries defeat stale snapshots. Financial observations/reconciliation remain available while normal mutations are fenced.

`LedgerService.recoverOperation` is required to become read-only in P06, intentionally narrowing its current alias-binding behavior. It retains current observation authority, existing alias/payload-conflict checks and matching business/receipt/outcome validation, but never calls `bindAlias`, creates RequestIdentity, invokes domain writes or otherwise changes financial rows. The rule applies to explicit recovery and `execute`'s uniqueness-recovery catch, even when admitted. A new key can observe an existing result without being bound. Only admitted `execute`/`runInTransaction` replay may bind a new request alias. Closed boot or restore admission therefore permits authorized observation without admitting an identity write; conflicts/unresolved evidence still fail safely.

Sweep broadcast-intent commit is the new-dispatch admission point. Pause blocks later admissions; already admitted work may finish sending and remains possibly sent/reconcilable. No lock spans external I/O; read/confirmation reconciliation continues during pause/weekends. Reconciliation balance reads use `/walletsolidity/getaccount` and `/walletsolidity/triggerconstantcontract`, bracketed by `/walletsolidity/getnowblock` on the same provider; retry if the solidified cutoff changes. Head-state balances are not consistent solidified evidence.

Every API/worker/signer boot creates a fresh in-memory UUID and registers FinancialRuntimeAdmission. Existing server startup injects process admission through app/router/service constructors into all LedgerService owners, including purchase/reward services. LedgerContext/client/job/env/restored state cannot choose a boot identity; missing binding fails closed. Financial mutations/dispatch wait for protected acknowledgement of that boot/current generation after inventory/history/attempt validation. Runtime roles may register only their own unacknowledged process-kind requests, never acknowledge/open them. Transactional admission rechecks UUID/generation; restore invalidates old boots. Stale OPEN/new API without tooling cannot mutate money. P06 tests actual startup; P11 proves supervisors/WAL/PITR/full restore.

Shutdown stops claims, records incomplete work and closes timers/DB/SSH/provider resources. Restart reconciles active attempts/provisioning before new dispatch. Operational health consists of safe scan lag/pending counts/recovery availability/shortfall/unresolved/fence status, not merely existing HTTP database health. Use existing logger with allowlisted events; do not log arbitrary Error messages, Buffers, ciphertext or nested provider payloads.

## Operational signals and operator ownership

P06 uses structured events through existing `infrastructure/logger/logger.ts`; the following event codes and config properties are proposed implementation requirements. Worker owns scan/pending/conflict events, signer owns recovery/resource/attempt events, and protected recovery tooling owns fence/admission transitions. The protected treasury/recovery operator is responsible for reviewing their protected process-log destination, investigating unresolved evidence, recovering storage/admission and arranging capped manual funding. Name the responsible person and demonstrate access to the designated log destination at operational acceptance; configuration/access is still unverified. This defines basic operator alerts without adding email, notifications, an event bus or a monitoring service.

| Proposed event / level      | Trigger and measurement                                                                                                                                                                                                                                              | Required response                                                                                                                                                |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SCAN_LAG / warn             | For READY assignments while scanning is admitted, server now minus `lastSuccessfulScanAt` (or `readyAt` until the first successful scan) reaches `scanLagAlertAfterMs`. Successful scan means a completed HOT window; historical page reads do not reset this clock. | Inspect provider/progress/retry state; retain durable candidates/windows. Intentional financial fencing is reported separately, not as a fabricated scan outage. |
| PENDING_WORK / warn         | Oldest nonterminal PENDING/VERIFYING/UNRESOLVED candidate age since `firstObservedAt` reaches `pendingWorkAlertAfterMs`; report bounded count/age, excluding ACCOUNTED/INELIGIBLE.                                                                                   | Investigate verification/provider/financial failure; do not discard work or invent credit.                                                                       |
| RECOVERY_UNAVAILABLE / warn | Required protected PUT/GET/LIST or acknowledgement validation remains unavailable after bounded retries, or separately escrowed decryption access is missing.                                                                                                        | Keep affected publication/signing unavailable and restore admission fenced where required.                                                                       |
| UNRESOLVED_ATTEMPT / warn   | First transition to UNKNOWN, or reconciliation cannot prove the original outcome/nonexecution.                                                                                                                                                                       | Reconcile the same attempt; retain the source claim and prohibit automatic replacement.                                                                          |
| RESOURCE_SHORTFALL / warn   | Fresh funds/activation/resources fail a required dispatch precondition, the current company-cost estimate exceeds its cap, or the estimate is unavailable.                                                                                                           | Keep the sweep safely waiting/unavailable and obtain operator review/capped manual funding; no zero-cost default or automatic top-up.                            |
| EVIDENCE_CONFLICT / error   | Assignment/receipt/attempt binding or immutable evidence disagrees, or required recovered financial history is missing.                                                                                                                                              | Retain the conflict and applicable fence; investigate without guessed balance, overwritten history or replacement transfer.                                      |
| RUNTIME_ADMISSION / info    | Financial fence, dispatch pause or boot/generation admission changes; a denied request is counted without per-request alert flooding.                                                                                                                                | Operator verifies the reason/evidence before acknowledging admission; existing confirmation/reconciliation continues.                                            |

`scanLagAlertAfterMs` and `pendingWorkAlertAfterMs` are validated integer process-config properties, each defaulting to 300000 ms with allowed range 1000-86400000 ms. They are diagnostic thresholds, not a detection SLA or commercial rule. Initial/state-change warnings emit once per affected scope; an unchanged ongoing warning may repeat at most once per 300000 ms, and one info recovery event clears it. A restart may repeat an unresolved warning; no exactly-once alert framework is required. Missing/stale resource evidence is unavailable rather than an invented zero balance/cost. Financial fencing/UNKNOWN safety never depends on logs or alert delivery.

Select flat allowlisted metadata before logging: event code, process kind, applicable assignment/candidate/attempt ID, safe state/reason code, bounded counts/ages and UTC server timestamp. No employee name/email, admin reason/reference, provider URL/body, key/envelope/path/digest, signed bytes or raw Error object/message enters these events. T043/T064 verify fixed-clock threshold boundaries, first/repeated/cleared transitions, protected operator guidance and captured safe logger output with sentinels. Normal tests use doubles/disposable boundaries; they do not establish a live alert destination or pass testnet/recovery acceptance.

## Acceptance evidence

Actual migrated DB roles, Linux filesystem/process identities, encrypted local storage and independent forced-SSH helper tests prove permissions/durability. Provider doubles cover malformed/finality/lost-ACK/timeout/retry/expiry races, but not actual chain/recovery acceptance. Opted-in testnet must record public provisioning/address, inbound/sweep TxIDs, raw log identities, exact credit/treasury amounts, finality, costs and recovered key/attempt outcomes. Missing config/access/funding/storage/coverage leaves the gate incomplete; no mainnet fallback follows.
