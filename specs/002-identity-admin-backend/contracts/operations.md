## Protected first administrator

The protected Linux CLI is owned by `apps/api/src/modules/admins/admin-bootstrap.cli.ts`, compiled to `apps/api/dist/modules/admins/admin-bootstrap.cli.js`. After building, run `pnpm --filter @template/api admin:bootstrap` from the workspace root under the authorized operator. The command accepts no arguments. Supply one strict JSON object containing fullName, email, password and reason through protected stdin, ending with EOF; input is limited to 8192 bytes. Do not put a password in a shell literal, command argument or checked-in input file. No public HTTP bootstrap endpoint exists. Other platforms fail closed for provisioning, while portable policy tests inject OS observations.

CLI-only `ADMIN_BOOTSTRAP_OPERATOR_UID` is a required explicit decimal nonroot UID (1–4294967294), with no default. Before stdin/database/provider access, read real UID, effective UID and username from Node's OS/process APIs (`process.getuid`, `process.geteuid`, `os.userInfo`). All observed UIDs must equal the configured UID and the OS-derived name must be nonblank/bounded to 128 characters. Missing/unavailable identity, root/elevation, malformed UID or mismatch exits with a safe authorization failure and no effect. Never trust argv/stdin actor fields, USER/USERNAME environment values or an identifiable account alone. Audit the trusted UID/name; configuration errors never echo values. Protect the launch configuration and database/provider secrets so only the selected dedicated operator/service principal can invoke provisioning; this OS access-control evidence is a launch prerequisite. Arbitrary holders of host/DB administration remain a documented compromised-host risk, not an application rescue capability.

Supply fullName, normalized email, password and nonblank reason through protected stdin. Password and credentials must not appear in command arguments, shell history, stdout/stderr, ordinary logs, audit snapshots or checked-in examples. Derive operator identity from the protected OS runner, not submitted actor fields; an unattributable runner fails closed. The program must validate complete bounded input and hash outside the transaction.

Under the singleton guard lock, reject if durable bootstrap completion already exists. Create one PENDING_VERIFICATION ADMIN, irreversible account/time marker and attributable identity audit atomically. The account receives ordinary email verification; only proof of email grants ACTIVE authority. Concurrent runners produce exactly one completion. Historical ADMIN accounts, including pending/inactive, initialize completion so setup cannot reopen. Later deactivation cannot reset the marker.

Send verification after commit with the bounded adapter. Provider rejection/unknown acknowledgement reports a safe nonzero delivery outcome while retaining completed bootstrap and recoverable pending admin. Retry ordinary bounded verification resend; rerunning bootstrap must refuse additional provisioning. Print only safe completion/account identifiers and outcome, never password/token/link/private provider diagnostics. The local development seed is not a production provisioning path.

## Resend boundary and failure semantics

Email adapter ownership is `apps/api/src/infrastructure/email/email-delivery.ts` and `email.service.ts`, with config in `core/config/resend.config.ts`. The production Resend path uses a bounded native-fetch transport; the installed Resend dependency is retained.

The verified provider request is `POST https://api.resend.com/emails`, Authorization bearer credential, JSON content type and Idempotency-Key. Allowlist `from`, `to`, `subject`, `html` and optional REST `reply_to`. Never honor `RESEND_BASE_URL` or a caller-provided origin; set redirect policy to error. See the [official endpoint](https://resend.com/docs/api-reference/emails/send-email).

Project-selected bounds are at most three attempts, 10 seconds per attempt through response-body consumption, and 64 KiB streamed response cap. Use Node 24 `AbortSignal.timeout(10_000)` and an injected transport for deterministic tests. Retry only HTTP 429/500/502/503/504, transport connection/response loss or timeout; waits before attempts two/three are fixed 100/250 ms. Do not extend waits from Retry-After. Other non-2xx responses, redirects, oversized bodies and malformed success/ID stop attempts. Conservatively classify network/timeout/response loss, any 5xx, 408/409, redirect and invalid/oversized 2xx as UNKNOWN. Other definite 4xx rejections, including 429, are REJECTED only if no earlier attempt was uncertain. Unclassified responses stay UNKNOWN. A valid later acknowledgement may resolve UNKNOWN; later rejection cannot. These limits and classifications are local policy, not provider guarantees. Validate successful provider ID; project errors to safe TIMEOUT, TRANSPORT, RATE_LIMIT, PROVIDER_UNAVAILABLE, PROVIDER_REJECTED, INVALID_RESPONSE or RESPONSE_TOO_LARGE classifications rather than logging provider bodies, rendered mail, request headers or tokens.

Reuse one idempotency key and identical payload within an attempt generation. Provider key retention is limited, so this is not permanent exactly-once delivery; see [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys). A new credential generation has a new key/payload. Do not retain raw action credentials or guess that a lost response means failure.

Registration and invitation state commits before dispatch. Record invitation attempt UNKNOWN before dispatch; update its delivery projection only if the generation and safe emailAttemptId still match. ACKNOWLEDGED means accepted by Resend API, REJECTED means a definite rejection with no earlier uncertainty, and UNKNOWN includes timeout, transport/response loss and interrupted dispatch. A later rejection alone must not erase earlier uncertainty. API acknowledgement never means mailbox delivery; see [provider event meanings](https://resend.com/docs/webhooks/event-types).

Registration/invite issue/reissue returns safe 503 on failed/unknown dispatch while retaining complete pending state. Public resend/forgot stays neutral. Recovery uses replacement/resend/reissue under limits; old links remain invalid. Audit and safe operational outcomes exclude provider payloads/passwords/hashes/credential links. All network calls occur outside transaction/retry bodies.

Before dispatch, verify the committed generation/attempt is still current, outstanding, unexpired and issued by an eligible ADMIN. Known closure/expiry or supersession skips sending and returns safe 409. A concurrent closure after that check may leave a late email carrying an unusable token; do not hold database locks across provider I/O. After I/O, condition delivery persistence on generation/attempt and reread current disposition. On acknowledgement, same-generation issue/reissue returns its freshly derived ACCEPTED/REVOKED/EXPIRED/PENDING projection with independent ACKNOWLEDGED delivery state; a superseded generation returns 409 without updating the new generation. A failed/uncertain dispatch returns 503 with intent retained. Generation checks apply before every retry; stop if known closed/superseded and retain any earlier uncertainty. Terminal disposition wins over later expiry, and response serialization never labels a revoked/accepted credential newly usable. Recipient validation/acceptance always rechecks live authority regardless of email status.

Populated cutover follows [historical-admin preflight](../data-model.md#forward-migration-and-compatibility-work). Only-ineligible historical admins halt cutover without bootstrap reopening, credential replacement or unaudited activation. Fresh databases may bootstrap; historical pending admins use ordinary verification resend/email proof, then ordinary ACTIVE password recovery when needed.

## Maintenance and API-schema cutover

For a separately authorized rollout, stop old API traffic and identity/financial writes before migration preflight. If any historical ADMIN exists, require an ACTIVE verified ADMIN or a PENDING_VERIFICATION ADMIN recoverable by ordinary resend/email proof. There is no standalone preflight CLI: the operator must inspect this predicate before deployment; the authority migration repeats it under an ACCESS EXCLUSIVE User-table lock.

Deploy through the existing root `pnpm db:migrate:deploy` command with the intended protected database configuration. Keep `20261003000000_identity_status` and `20261003000100_identity_authority` in order. The first commits enum additions; the second wraps viability, backfill, credential invalidation and protections in one explicit transaction. Preserve applied auth/P01 migration files and existing financial rows.

The authority migration deletes legacy refresh rows and clears verification/reset hash-expiry pairs. Old access tokens without sessionId are rejected by the session-bound API. Require fresh eligible login, pending verification resend and new ACTIVE-account recovery links; do not enable a legacy-token bypass. Generate reviewed Prisma types with `pnpm db:generate`, build the matching API, validate its production configuration and schema, then resume only that API after cutover checks pass. These preparation commands need DATABASE_URL even when they do not connect; integration tests supply their own isolated URL.

If the authority migration fails, keep traffic fenced and confirm its transaction rolled back. Enum additions may remain committed and grant no authority. Resolve the actual cause; historical lockout needs a separately authorized recovery decision. If Prisma recorded this exact failed migration and rollback has been verified, `pnpm --filter @template/database exec prisma migrate resolve --rolled-back 20261003000100_identity_authority` records that rollback before a reviewed retry of `pnpm db:migrate:deploy`. This changes migration tracking, not application recovery. Do not mark the migration applied, reopen setup, infer sponsors/balances or resume the old API to bypass a failed gate. No production cutover or migration-resolution command was executed for P02 acceptance.

Identity transactions use maxWait 5000 ms, timeout 10000 ms and at most three attempts without deliberate delay. Retry only P2034 or known P2010 adapter failures whose driverAdapterError.cause.originalCode is 40001/40P01; each attempt rechecks live authority, expiry and intent. Stale versions, uniqueness, validation and provider outcomes are not transient retries. Generated referral-code collisions have their separate exact-constraint three-attempt bound. Hashing and network I/O stay outside transaction retries.

## Effective rate-limit topology

Retain installed express-rate-limit and its MemoryStore for an explicitly verified **single API process**. Current source launch scripts establish an entrypoint, not production topology. Counters disappear on process restart and are not shared across workers/replicas. Do not describe this evidence as global or distributed protection.

The following are implemented default bounds, not claims of deployed protection. Bounded environment overrides remain in `core/config/auth-rate-limit.config.ts`; `modules/auth/auth.rate-limiters.ts` and `modules/admins/admins.routes.ts` own enforcement.

| Operations                                             | Default bucket limits                                                                                                                                                            |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing registration                                  | 5/source/hour.                                                                                                                                                                   |
| Existing verification; **new** verification validation | 20/source and 5/token per 15 minutes.                                                                                                                                            |
| Existing verification resend                           | 20/source and 5/account per hour; retained 60-second replacement cooldown.                                                                                                       |
| Existing ordinary login; **new** admin login           | Shared 20/source and 5/source+account per 15 minutes.                                                                                                                            |
| **Changed** refresh keys                               | Retain 60/source+credential attempt protection; add 60/source before credential checks and 60/verified source+stable-session per 15 minutes so rotation cannot reset the budget. |
| Existing forgot password                               | 20/source and 5/account per hour.                                                                                                                                                |
| Existing reset/validation                              | 20/source and 5/token per 15 minutes.                                                                                                                                            |

Numerical tests must verify rejection, replacement cooldown and bucket sharing without exposing credential keys.

Before deployment acceptance, verify every API request reaches the same limiter process and the source key matches the validated proxy boundary. If topology needs additional processes/replicas, FR-033 remains blocked until an appropriate shared store and fail-closed store-failure tests are implemented. This plan does not provision speculative Redis/PostgreSQL limiter infrastructure.
