# P05 Existing UI Integration Contract

**Status:** Proposed PLAN design, 2026-10-05. No P05 application implementation or acceptance test execution is established by this document. Frontend work starts only after Gate B in [plan.md](../plan.md). Shared wire contracts are defined in [http-api.md](http-api.md); persisted identities and snapshots are defined in [data-model.md](../data-model.md).

## Authority and Presentation Boundary

The nine existing routes below are the complete P05 frontend scope. Keep their App Router pages, layouts, navigation, section order, Cairo/Arabic/RTL/light styling, icons, dimensions and breakpoints. Keep the existing promise-valued route parameters and the Suspense boundaries around employee tasks and code creation. Use existing client feature adapters/hooks and central Axios transport; introduce no Server Action business path or request-independent server cache of private data.

- Accepted C1 permits necessary truthful task/review/calendar/fixed-schedule wording and removal of the employee demo-code disclosure. Pending submission is not credited money; rejection deducts nothing; final decisions cannot be reversed; the next window comes from the server's next eligible Baghdad work date.
- Accepted C2 permits minimal local availability/final/retention/declaration/feedback states, required review reasons, distinct material-action confirmations, final-action restrictions and fixed single-date schedule controls. Reuse existing control/dialog styles and the existing review popup, allowing only necessary local labels and space. Do not add a route, standalone screen, recurring scheduler, image gallery or redesigned popup.
- These exceptions do not authorize global fixture-provider removal, employee-detail task/code tabs, dashboard/home/account/policy integration, deposits or withdrawals. Those remain their roadmap owners. Unrelated fixture consumers remain available, but none may authorize P05 production work or wallet effects.

## Employee Work and Evidence Lifecycle

1. `GET /tasks/today` supplies `serverNow`, business date, opening/cutoff/next eligible opening, availability/restriction reason, current task revision/content/link/illustration, unlock state and any accepted own submission. Its `currentEntitlement` supplies the prospective saved package/reward display before submission; Free/expired has no invented reward. Use the submission's captured reward, declaration, evidence/version, decision and `canReplace` fields when one exists. Do not substitute today's package reward or current task instructions for accepted submission snapshots.
2. Upcoming, closed, holiday, no task, Free, expired and task-restricted states have no new-work action. A withdrawal-only restriction does not independently disable eligible work. A read/upload/processing failure is unavailable/error state, never an open task, empty history, fixture image or zero reward. Existing accepted work remains inspectable by its currently authorized active owner even if paid entitlement expires or task work is restricted.
3. Gated work posts the entered code with `commandId` and `expectedTaskRevision` to `POST /tasks/:taskId/unlock`. The returned employee unlock result is the only unlock authority. Pausing a code does not reset a saved unlock; repeated successful usage does not increase counts or consume a daily claim. Do not retain admin code collections in employee bundles or expose the fixture demo code.
4. Selection creates only a temporary local preview. The submission workflow uploads one actual file to `POST /proofs` with its own upload `commandId`, obtains a ready `proofAssetId`, then posts `declaredExecuted: true`, the selected task identity/current revision and that asset ID to `POST /task-submissions`. Blob/external URLs never enter the business command. Keep a saved ready asset available to a permitted retry after a definitive business validation conflict; do not discard the previously accepted submission's evidence on upload or replacement failure.
5. Submission success is pending work with unchanged spendable/reserved balances. A stale task revision consumes no daily claim; preserve safe local input, refresh the task, and require work matching current instructions before another confirmed submission within the same window. A rejected claim still consumes the date, so rejection shows a final result rather than the submission form.
6. Replacement posts `commandId`, `expectedSubmissionVersion` and the new ready owner-bound proof to `PATCH /task-submissions/:submissionId/evidence`. It requires the saved pending claim, current employee work eligibility and its original cutoff. It does not require re-entering a code or matching the task's later revision. Preserve captured declaration/reward/subscription/instructions/link and the original deadline. Render replacement feedback in the existing pending branch. At cutoff or final decision, disable both visible controls and handlers.
7. Read history through employee-owned `GET /task-submissions`, with bounded page/limit and the accepted status filter. Use existing history/card/Button styles for local previous/next navigation without adding another page. The owner can inspect a selected accepted submission's saved proof, captured declaration and decision within the existing task-card/history section, reusing its image/feedback treatment without another popup. A final proof removed after permitted retention is explicitly unavailable while declaration, decision, reward and submission metadata remain visible. Do not display a fixture as missing evidence.

## Private Preview and Account Isolation

`GET /proofs/:assetId` and `/content` are authenticated private resources. The proposed preview hook must fetch binary content through the existing central bearer transport with an `AbortSignal`, validate expected image content type/size and returned asset/resource ownership, and create an account/resource-owned blob URL for the existing image element. A bare API URL in `<img>` cannot supply the memory-only bearer token. Do not expose storage paths, add query-string credentials, place evidence in `public/`, use the Next image optimizer, or persist proof bytes/object URLs in localStorage, shared diagnostics or long-lived cross-account caches.

Keep binary bytes and object URLs in the preview owner's transient lifecycle, outside Query cache data. Authorized safe asset metadata may use the scoped query owner. The binary response is an image, not a JSON success envelope; apply the canonical stored-output byte cap from research rather than the smaller original-upload cap.

Task illustration uploads use `POST /admin/task-illustrations`; employee-authorized reads use `GET /task-illustrations/:assetId` and `/content`, bound to permitted current task or accepted-history access. Admin read authority and proof/illustration purpose checks follow [http-api.md](http-api.md). Both use the canonical raster output and finite file/resource budgets in [research.md](../research.md). Do not use a proof identity as an illustration or treat an admin-only content URL as a renderable employee image.

The installed Next 16 image documentation states that the default optimization loader does not forward authorization headers and writes optimized results to a disk cache. Preserve the existing image presentation with a scoped browser blob; `unoptimized` alone does not supply bearer authority. The relevant version-matched guides inspected for this contract are `apps/web/node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md`, `01-app/03-api-reference/03-file-conventions/page.md` and `01-app/03-api-reference/02-components/image.md`.

Cancel pending private reads and revoke object URLs on replacement, preview close, unmount, resource change, logout, confirmed access loss and session retirement. Recheck initiating session account/role/epoch/check plus resource/evidence identity immediately before admitting bytes or completion. An obsolete response must be discarded and any URL it created revoked. Failed refresh must not expose stale evidence or reopen protected actions; keep permitted drafts and safe retry feedback.

Existing `services/api/session-runtime.ts`, `features/auth/hooks/auth.hooks.ts`, `services/api/safe-error.ts`, `services/api/api-client.ts` and `shared/query/query-client.ts` remain the authority, transport and cache owners. Proposed P05 query keys include non-secret account, role, epoch/check, domain, resource, filters and page. Reuse the existing `shared/query/financial-query.ts` through a bounded P05 namespace extension: its current keys and retirement cleanup are explicitly `p04`, so merely importing it does not provide P05 cleanup. Preserve P04 keys/caller behavior and deliberately include both namespaces in session retirement cancellation/removal. Update the central private-read denial classification alongside the P05 denial-aware read owner to prevent repeated revalidation loops; no feature-local competing token/refresh stack.

## Commands, Review and Reconciliation

- Strict shared schemas bind the target, normalized input, expected revision/evidence, `commandId` and distinct confirmation. Every material admin create/edit/status command includes `confirmed: true`; approval and rejection also include a required server-validated reason. Current actor/time/entitlement/amount are never writable form fields.
- The existing `AdminConfirmDialog` already accepts reason/loading/error/disabled state and prevents its own overlapping confirmation. Its local guard is insufficient across close/remount/resource change: a focused command owner retains the original outstanding operation until terminal observation. Await the actual command; do not close, navigate, toast success or mutate wallet state on simulated timers.
- A review opens an authoritative selected submission read and private current evidence, declaration, captured instructions/link/reward and evidence history in the existing popup. `POST /admin/task-submissions/:submissionId/review` binds `expectedSubmissionVersion`, `expectedEvidenceVersion`, decision, reason and confirmation to that reviewed state. Replacement since review causes a conflict and evidence refresh before a new confirmation. The existing popup's focus containment/Escape/restoration/background lifecycle must be made usable locally, reusing existing shared dialog background behavior.
- Mutations keep `retry: false`; no offline replay, optimistic approval, new-key financial retry or guessed reversal. An in-flight guard is checked in handlers as well as disabled controls. Its ownership includes actor and target so an old completion cannot close or populate a newly selected record.
- For a lost task/code/submission/review response, read its actor-owned outcome via GET `/task-commands/:commandId?kind=...`. OBSERVED is committed; CANCELLED is an irreversible unused-key fence; NOT_OBSERVED remains uncertain. In the existing C2 feedback area, provide a deliberate cancel/resolve action using existing control/confirmation styles and POST `/task-commands/:commandId/cancel`; add no popup or route. A committed result may win that race and must be presented truthfully. For uncertain uploads, use the separate purpose-bound observation and cancellation routes, not a TaskCommandRecord lookup. READY/FAILED is durable terminal; PENDING/NOT_OBSERVED is not. READY cancellation preserves accepted bytes/retention.
- Before dispatch, local validation may release an unsent handle. After dispatch, keep the original guard through raw errors, reset/close/remount and lost replies until a validated durable terminal result. A rejection without a terminal fence still needs explicit resolution. A lost cancellation response keeps the same handle for observation or deliberate repeat of cancellation; never automatically resend the business command/file. A confirmed unused-key cancellation permits a fresh authoritative eligibility/resource read and deliberate new confirmed intent/file selection with a new key. Preserve permitted drafts without retaining private payloads across account teardown; refresh after cancellation without reporting business success or invalidating money as if approved. Scope-check terminal completions exactly like every other completion, so old account/resource results cannot reopen controls or restore private content.
- Browser coordination may retain only bounded actor/operation/target/command handles for reload/cross-tab observation, never proof bytes, entered code, declaration text, review reason or private command payload. Reuse the existing session/runtime coordination conventions without copying the purchase quote/package-specific APIs as P05 authority. Missing required coordination is a truthful unavailable state.
- After validated saved outcomes, invalidate/refetch relevant P05 today/submission/history/task/code/usage/review scopes. Approval additionally invalidates existing P04 wallet/ledger and affected admin finance/wallet scopes. Rejection/replacement/unlock do not adjust money. Other sessions reconcile on focus/manual refresh and bounded pending reads, stopping at final states. Session teardown is the only ordinary reason to clear all private caches.
