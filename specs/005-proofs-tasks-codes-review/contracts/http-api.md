# P05 HTTP API Contract

**Status**: Proposed design, not implemented routes. Base prefix is existing `/api/v1`. Schemas will be owned by `packages/contracts/src/proofs/`, `tasks/`, `task-codes/` and `task-submissions/`, exported through `@template/contracts`. Persistence is in [data-model.md](../data-model.md); file budgets in [research.md](../research.md); UI consumers in [ui-integration.md](ui-integration.md).

## Common protocol and authority

- Reuse `successEnvelopeSchema`, `errorEnvelopeSchema`, `ResponseHelper` and existing HTTP pagination semantics. Every JSON adapter validates unknown envelope and endpoint data. Binary raster content is not a JSON envelope. Return canonical exact decimal USDT strings and UTC ISO instants; Baghdad business dates are `YYYY-MM-DD`.
- Every listed route requires bearer authentication, current ACTIVE/verified account and live session. Employee routes require USER; admin routes require ADMIN. Existing writes retain CSRF and applicable rate limits. Recheck current authority/resource state before consequential writes and private reads. Anonymous/revoked/disabled receives 401; authenticated wrong role or known own work restriction 403; missing/foreign/private-purpose resource returns uniform 404 without private metadata. No GET/HEAD changes business state.
- All input objects are strict; reject employee/actor/date/reward/subscription/balance/decision-authority/storage-path fields not explicitly declared. UUID IDs and bounded positive versions prove neither authority nor existence. `declaredExecuted` and `confirmed` must be literal true where required, not truthy coercions.
- JSON command `commandId` is a UUID scoped to authenticated actor and operation kind. Same accepted identity/payload returns its original safe outcome; changed payload conflicts. Hash includes target, normalized consequential fields, versions, decision/reason/confirmation. Daily/unlock/final-reward uniqueness applies independently of keys. Replays still require current observation authority.
- Business-command success is 201 on creation, 200 on update/unlock/review; accepted replay returns 200 with its recorded outcome. Invalid schema 400/`VALIDATION_ERROR`; stale/domain/idempotency/uniqueness/final conflict 409 with a safe P05 code. No 204 is needed. Required reason is nonblank <=500 characters; normal human content is not destructively normalized. No private raw payload, SQL, decoder detail or storage path appears in errors/logs.

## Bounded field and list conventions

Proposed task editable fields: `title` nonblank <=150 characters; `description` nonblank <=10,000 including instructions; `targetUrl` <=2,000, parsed HTTP(S), hostname required, no credentials/control characters, reject localhost/private literal targets. No server fetch/import follows a task URL. `platform` nonblank <=80 characters is free text, preserving the current task form; it is not restricted to the four existing list-filter options. `publicationDate` must be a valid weekday Baghdad date; `publicationState` is PUBLISHED/PAUSED/CLOSED; `isCodeRequired` boolean; `illustrationAssetId` nullable UUID. Field omission in PATCH means unchanged, explicit null removes optional illustration. Do not accept date ranges or start/end hours.

Codes accept nonblank text <=64 characters after surrounding-whitespace trim and uppercase normalization, rejecting embedded control characters. Global normalized uniqueness covers every retained state. `description` nullable <=500 characters. Task ID/text are immutable after creation. Preserve the accepted code character domain consistently between shared normalization and database checks; do not add an unapproved commercial use cap.

Lists use strict `page`/`limit` (defaults 1/25, max 100), safe offset arithmetic, bounded `search` <=150, allowed enum/status/date/UUID filters only. Return `data: {items, pagination}` plus matching envelope `paginationMeta`, reusing existing page schemas/helpers. `total` uses the same permission/filter predicate and one RepeatableRead snapshot as rows. Empty total means zero pages. Stable ordering includes unique ID tie-breaker; paging does not promise a frozen dataset across later reads.

`EmployeeTaskDay` is a strict DTO with `serverNow`, `businessDate`, `window: {opensAt, closesAt, nextOpeningAt}`, `calendarState` (UPCOMING/OPEN/CLOSED/HOLIDAY), `workEligibility` (ELIGIBLE/FREE/EXPIRED/TASK_RESTRICTED), `opportunityState` (PUBLISHED/PAUSED/CLOSED/NO_TASK), `task` nullable, `unlock` nullable and `submission` nullable. `currentEntitlement: {effective, packageCode, packageLabel, dailyReward}` supplies the existing pre-submission package/reward display from the effective subscription's saved terms; Free/expired has null prospective package/reward fields, not fixture/default money. This read is indicative; first submission revalidates/captures after locks. Accepted submissions use their own captured reward regardless of later entitlement. `canUnlock`, `canSubmit`, `canReplace` and an allowlisted `unavailableReason` describe actions independently of existing accepted work. Holiday returns no new opportunity; no task/unavailable result cannot fabricate an open task. Denied identity is an auth error, not an availability DTO. The server returns the next eligible calendar opening for truthful wording; this is not a promise that a task will be published then.

Employee `task` includes ID, current revision, one publication date/content/link/platform, safe optional illustration metadata and gating requirement, without code text or usage. If accepted work exists, rendering uses its immutable task/reward snapshots instead of current opportunity values.

`SubmissionSummary` includes ID/task/date, captured task title/revision, status, captured reward string, submittedAt/deadlineAt, version/currentEvidenceVersion, declaration and final decision summary if present. `SubmissionDetail` adds captured instructions/link/platform/subscription terms, ordered bounded evidence metadata and `canReplace`; evidence history is itself pageable when it exceeds one response limit. Each evidence item has version/acceptedAt/asset ID/read availability and safe image facts, no path/bytes. `decision` is null while pending; final decision includes APPROVE/REJECT, reason, time, reviewed versions and reward operation ID only for approval. Employee display does not require exposing reviewer private email.

`UnlockOutcome` includes task ID/date, unlockedAt, unlock identity and accepted task revision plus current day result; no reward/payment outcome. A later task content revision still requires fresh work/revision on first submission.

## Asset upload, observation and binary routes

| Method/path                                                | Input                                             | Result and authority                                                                                                                                                           |
| ---------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

| POST `/proofs/uploads/:commandId/cancel`                   | UUID; `{confirmed:true}`                          | Current USER fences only its own PROOF upload key; 200 terminal UploadObservation, FAILED/UPLOAD_CANCELLED if absent/STAGING, accepted metadata if READY already won.          |
| GET `/proofs/:assetId`                                     | UUID                                              | Current active owner or current ADMIN; safe `ProofAsset`, including retained availability. Active Free/expired/task-blocked owner may inspect own accepted evidence.           |
| GET `/proofs/:assetId/content`                             | UUID                                              | Same current owner/admin/purpose policy; canonical PNG bytes only if READY and retained file present. No static URL/optimizer.                                                 |
| POST `/admin/task-illustrations`                           | Same bounded multipart                            | Current ADMIN; purpose TASK_ILLUSTRATION, 201 ready `IllustrationAsset`. No employee proof identity may substitute.                                                            |
| GET `/admin/task-illustrations/uploads/:commandId`         | UUID                                              | Current uploading admin's purpose-bound observation.                                                                                                                           |
| POST `/admin/task-illustrations/uploads/:commandId/cancel` | UUID; `{confirmed:true}`                          | Current ADMIN; same terminal cancellation for its own TASK_ILLUSTRATION key. Purpose derives from route; no arbitrary owner/purpose.                                           |
| GET `/task-illustrations/:assetId`                         | UUID                                              | Current ADMIN or employee authorized for a referencing current task/own accepted task history; safe illustration facts. Unattached illustration is admin-only.                 |
| GET `/task-illustrations/:assetId/content`                 | UUID                                              | Same task/role/purpose policy; canonical PNG binary.                                                                                                                           |

`ProofAsset`/`IllustrationAsset` contains asset ID, purpose, uploadedAt, safe width/height, output content type/byte count and availability PRESENT/REMOVED/STORAGE_UNAVAILABLE. Never expose storage key, input filename, hashes, filesystem location or raw upload bytes. Purpose is checked before response. No new work may attach unavailable/deleting/unready files. A retained metadata read may return REMOVED after permitted cleanup; content then returns 410/`PROOF_REMOVED` only after current authorization. Missing file before permitted cleanup returns 503/`STORAGE_UNAVAILABLE`, preserving retained metadata; never report successful deletion or fake image. Wrong purpose/foreign/missing uses 404 before any content result.

Binary success: 200 `Content-Type: image/png`, correct bounded `Content-Length`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, `Content-Disposition: inline` with a fixed safe server filename and no client metadata. No response/optimizer/shared cache credentials. No public redirect, permissive SVG or JSON-in-image fallback. Current authorization is checked immediately before opening the allowed contained file; do not retain DB transactions across streaming. Existing opened reads may finish while permitted final cleanup unlinks on supported filesystems; otherwise truthful availability/retry, with no pending evidence deletion.

Upload input budget is 5,242,880 bytes inclusive; total multipart body 5,259,264; original PNG/JPEG/WebP must agree with MIME/signature/decoded format and fully decode. Exactly one frame; APNG/animated WebP fixtures must be rejected by verified bounded container/decoder checks. All other finite budgets are in research. Canonical returned binary may be up to 33,554,432 bytes; binary consumers must use this output cap, not the raw-file limit.

Authenticate/CSRF/role before parser admission. Count chunked/declared total bytes independently and reject compression/extra/duplicate/truncated parts. Validate literal part names and <=32-byte field names explicitly; the selected parser does not enforce multipart `fieldNameSize` itself. Header pair/byte options bound parser work but do not alone prove rejection of excess headers; test required shape/content parsing and finite memory without inventing an automatic error. Application rejects malformed required headers/type/identity and duplicate/unknown parts. The whole input stream has a 30-second maximum deadline (or shorter existing request deadline), independent of the child processing deadline; disconnect/timeout cancels streams and durable pending lifecycle safely.

Admission 429/`PROOF_PROCESSING_BUSY` for occupied bounded slots; byte overflow 413/`UPLOAD_TOO_LARGE`; unsupported type/animation 415/`UNSUPPORTED_IMAGE`; malformed decode/dimensions/output validation 400/`INVALID_IMAGE`; exhausted storage/failed native processing 503/`STORAGE_UNAVAILABLE` or `IMAGE_PROCESSING_UNAVAILABLE`. No READY/claim/reward results from failure. Upload hash binds actual bounded bytes and purpose; same scoped command/different bytes conflicts, uncertain success observes original upload. Temporary failures are not automatically financial retries.

### Existing-screen projections

- `AdminTaskSummary` includes ID/title/platform/date/revision, fixed window, gating, publicationState/displayStatus, `linkedCodeCount`, `distinctUnlockedEmployeeCount`, `submissionCount` and `approvedSubmissionCount`, computed over the complete authorized associated records. Display status is CLOSED after the task cutoff or explicit CLOSED; otherwise PAUSED for paused publication, SCHEDULED before its opening, ACTIVE in its published window. Search covers title/platform/ID; platform filters preserve Google Maps/Trustpilot/YouTube/App Store options while other free-text platforms remain visible under all. Status/platform filters and counts use server clock/predicates, never just page rows.
- `AdminCodeDetail`/summary includes creator safe display, createdAt/updatedAt, description, associated task ID/title/platform/window and `distinctSuccessfulEmployeeCount`/`successfulUsageCount`. Search covers normalized code/task title/creator display; usage search covers employee name/email/ID. Existing `/admin/codes?task=<id>` maps to backend `taskId`; existing creation `?taskId=<id>` remains. Usage and code-audit pages supply those retained existing sections.
- `AdminSubmissionSummary` includes employee ID/name/email, captured task title/reward/date, submittedAt/status/version, current evidence version and safe asset metadata/availability for an authenticated thumbnail. No public image URL or bytes. List data additionally contains `statusCounts: {all,pending,approved,rejected}` over the complete authorized set with non-status filters applied; page total also applies the selected status. These totals are not the length of the current page.
- Final-review wire intent APPROVE/REJECT maps explicitly to persisted APPROVED/REJECTED states. Summary/detail decision projections use the declared wire decision names consistently; no status alias implies reversal or another financial operation.

### Upload terminal resolution

Every UploadObservation includes its commandId and route-derived purpose. PENDING and NOT_OBSERVED are nonterminal. FAILED contains a bounded durable failureCode/server failedAt; UPLOAD_CANCELLED identifies an irreversible unused-key fence and contains no invented file/hash/upload-time facts. READY means acceptance previously committed and includes safe retained asset metadata with current PRESENT/REMOVED/STORAGE_UNAVAILABLE availability, even if current lifecycle state is DELETING/DELETED; it never promises removed bytes exist.

Cancellation retains bearer/current-session/role/CSRF/limits, own purpose-bound identity and does not require current paid/task eligibility simply to abandon unused work. Under existing actor/session then asset locks and owner/purpose/key uniqueness, absent intake inserts FAILED/UPLOAD_CANCELLED; STAGING becomes FAILED and revokes its lease; existing FAILED returns unchanged; accepted READY/DELETING/DELETED is never cancelled or deleted. Registration and READY/restart completion check the same fence and original live upload session/lease. Late cancelled-key intake receives 409/UPLOAD_CANCELLED. Cleanup/abort/reaping/unaccepted unlink is external to transactions; keep capacity until done. A lost cancel response observes or deliberately repeats that same cancellation. Never resend file bytes automatically or treat absence as failure.

## Command observations and conflicts

`CommandObservation` is `{state: OBSERVED, command: {kind, commandId, targetId, committedAt, outcome}}`, `{state: CANCELLED, commandId, kind, cancelledAt}` or `{state: NOT_OBSERVED, commandId, kind}`. Proposed kinds cover task create/edit/status, code create/status, unlock, submit, evidence replace and final review; names are exported once and mapped to P05 records. GET `/task-commands/:commandId?kind=...` changes nothing. OBSERVED maps to COMMITTED; current resource authorization still applies. CANCELLED exposes only the caller's own irreversible unused-key fence, with no pretend target/outcome/payload. NOT_OBSERVED remains nonterminal.

POST `/task-commands/:commandId/cancel` takes strict `{kind, confirmed:true}` and returns 200 CommandObservation OBSERVED or CANCELLED. Require bearer/current active verified role/session, CSRF and bounded critical-action limits. USER may cancel its own unlock/submit/evidence-replace keys; ADMIN its own task/code/review keys. No paid/task restriction check is needed merely to cancel an unused own key. Execution and cancellation share the existing sorted actor-user lock held through commit; every executor checks the unique terminal receipt before effects. If COMMITTED won, return its permitted outcome, subject to current resource access. Otherwise append/reuse CANCELLED. A late original or any changed payload under that cancelled key gets 409/COMMAND_CANCELLED and zero effects. Cancellation of committed financial work cannot reverse it; ordinary resource authorization failure exposes no saved private outcome.

Useful proposed safe codes: `TASK_REVISION_CONFLICT`, `TASK_DATE_LOCKED`, `TASK_DATE_OCCUPIED`, `CODE_ALREADY_EXISTS`, `TASK_WINDOW_CLOSED`, `TASK_UNAVAILABLE`, `TASK_ELIGIBILITY_DENIED`, `DAILY_CLAIM_EXISTS`, `SUBMISSION_VERSION_CONFLICT`, `EVIDENCE_VERSION_CONFLICT`, `SUBMISSION_FINAL`, `ASSET_NOT_READY`, `IDEMPOTENCY_CONFLICT`. Their runtime definitions/routes/OpenAPI/tests must be created together; these are planned codes, not current API claims. Positive own domain errors use 409 where state changed, 403 where current work restriction denies, and 400 where shape is invalid.

Before dispatch, client validation may release a never-sent local handle. Once dispatched, a raw validation/access/conflict error without a durable terminal result does not permanently fence the key: retain the safe error/draft and resolve the original handle. Only validated OBSERVED/CANCELLED or durable upload READY/FAILED retires its guard; timeout, NOT_OBSERVED or dialog reset cannot. Explicit cancellation is deliberate and idempotent; a lost cancellation reply may be observed or deliberately repeated under the same key. After CANCELLED, refresh current resource/eligibility and require a deliberate new confirmation/key; upload FAILED similarly requires deliberate new eligible file selection/key. No automatic feature business/upload retry. Independent-key duplicate submissions/reviews remain protected by business uniqueness; opposite/stale finals cannot change history.
