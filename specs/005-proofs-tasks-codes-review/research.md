# P05 Research: Private Proofs, Tasks, Codes, and Review

**Date**: 2026-10-05 | **Feature**: `specs/005-proofs-tasks-codes-review`

This is design research for the clarified [specification](spec.md), not implementation or test evidence. The operating contract, constitution 1.0.0, whole roadmap and all eight engineering guides govern the decisions. The owner authorized bounded preimplementation amendments on 2026-10-05 following ANALYZE findings U1/U2/I1. Native-resource acceptance and terminal command/upload recovery are specified below; their implementation and behavioral evidence remain future Gate B/F work. No business clarification is reopened.

## Existing foundation and predecessor evidence

- **Decision**: Reuse P01-P04 rather than rebuild money, authentication, subscriptions, wallet or browser infrastructure.
- **Rationale**: `apps/api/src/modules/ledger/ledger.service.ts` exposes `runInTransaction` and transaction-scoped credits with `TASK_REWARD`/`NON_REFERRAL` already supported. `modules/subscriptions/subscriptions.service.ts` exports `currentSubscription`; `subscriptions.mapper.ts` evaluates effective activation/exclusive expiry. `core/business-calendar/business-clock.ts` uses Luxon 3.7.2 and Baghdad. `modules/auth/session-authority.ts` checks current account/session/role; identity transaction helpers protect user mutations. The current schema contains these foundations but no P05 entities. `specs/003-auth-account-frontend/tasks.md` records T001-T065 complete; `specs/004-packages-referrals-wallet-finance/tasks.md` and its quickstart record T001-T078, Gate B/F, 1,178 fresh package tests and 77 browser scenarios. These are reused local records; root lint/types/build include explicitly recorded unchanged Turbo cache hits. They are not fresh P05 results or launch approval.
- **Alternatives considered**: A second ledger/auth stack, replacing the calendar or assuming the historical engineering-guide inventory is current would duplicate completed work and lose accepted protections. Missing P05 endpoints are proposed work, even though the ledger accepts the origin.

## Calendar and immutable daily opportunity

- **Decision**: One retained `Task` per weekday publication date, a simple revision and publication state `PUBLISHED`/`PAUSED`/`CLOSED`; derive upcoming/open/closed/holiday from Baghdad date/window. Add focused window/next-opening output to the existing calendar owner, not a scheduler. Freeze the task's date through a monotone first-participation timestamp and relational constraints once an unlock or submission commits.
- **Rationale**: The current task screens have scheduled/active/closed presentation, not a separate draft product. A unique retained publication date prevents replacing a paused participated opportunity with a second task. Before participation, an audited revision-checked date edit may move to an unused weekday; afterward another date needs another task and globally distinct codes. First submissions send the current revision; task edits and participation take the same task lock. Acceptance time is obtained after locks, so an upload started before 18:00 cannot extend work.
- **Alternatives considered**: A publication-slot table, recurring scheduler or task-version registry adds no needed capability. Browser times and configurable start/end fields violate the fixed rule. Mutable date attribution or a unique subscription/day claim fails upgrades and the clarified date rule.

## Claims, replacement and final review

- **Decision**: Persist one `TaskSubmission` per employee/Baghdad date with captured current task content/link/revision, subscription, reward, declaration and original cutoff. Append `SubmissionEvidence` versions for replacements. Bind a single `FinalReview` to the exact current evidence/submission version.
- **Rationale**: First submission captures the active subscription while holding the same user lock used by purchases/restrictions. Pending work has no wallet effects. Replacement checks current employee authority/paid eligibility and the captured cutoff, retaining entitlement and declaration; it does not require a new unlock or current task revision after valid acceptance. Rejection consumes the accepted daily claim, posts no money and is final. Approval after employee expiry/ban uses the captured reward, while current administrator authority remains mandatory.
- **Alternatives considered**: Overwriting proof pointers without evidence history loses what was reviewed. Rechecking current package rewards at approval changes accepted terms. A final reversal, clawback or reject-to-resubmit path is excluded.

## Atomic approval and lock order

- **Decision**: Approval enters the existing `LedgerService.runInTransaction`, then takes P05 locks; credit uses namespace `p05.task-reward`, business key submission UUID, origin `TASK_REWARD`, source `NON_REFERRAL`, and the captured exact amount. Commit the final decision, domain audit/command, financial operation/posting/audit and wallet together.
- **Rationale**: Existing `ledger.transaction.ts` locks sorted users, sorted wallets and reservations under Serializable, with at most three attempts for recognized transaction conflicts. Preserve that order, then current session authority, task, code when needed, submission, and sorted assets. The employee wallet owner need not still be active; the admin actor must. Nonfinancial P05 commands use the identity lock/retry primitives and the injected phase clock after locks. No transaction includes decoding, filesystem or network I/O. [PostgreSQL row locks](https://www.postgresql.org/docs/18/explicit-locking.html) and [isolation](https://www.postgresql.org/docs/18/transaction-iso.html) explain the chosen ordering/retry boundary; installed Prisma and existing source determine the actual API calls.
- **Alternatives considered**: Locking a submission and then entering the ledger can invert existing user/wallet order. A browser/queue lock, mocked transaction or ledger-only credit cannot prove one final status/reward/audit. A new accounting framework is unnecessary.

## Domain command identity and audit

- **Decision**: Add focused immutable `TaskCommandRecord` terminal rows, unique by actor, operation kind and command UUID. COMMITTED retains the normalized intent hash, typed target, safe saved outcome and material-admin before/after facts; reviews retain the required reason. CANCELLED fences an unused identity without inventing its missing payload or business result. Upload identity and cancellation belong to the existing asset lifecycle, separately.
- **Rationale**: Financial `RequestIdentity` requires a financial operation and cannot cover rejection/publication/unlock. P04 `ConfigurationChange` belongs to package/referral settings. Existing `IdentityAuditRecord` has identity-only SQL checks, and the financial CREDIT audit does not own task-review reasons. The domain record provides auditable accepted changes and lost-response observation without weakening either audit. The review hash includes target, both expected versions, decision, reason and confirmation; the ledger intent hash alone omits some of these facts. Accepted same-key/different-payload requests conflict; domain uniqueness remains effective for new/absent keys. Observation `NOT_OBSERVED` is not proof that an earlier request cannot still commit.
- **Alternatives considered**: Extending an unrelated audit or building a universal command/outbox framework would obscure ownership. Treating NOT_OBSERVED or elapsed time as failure permits late execution; permanently retaining the guard provides no recovery. Explicit cancellation fences the original identity without automatically retrying a financial action.

### Terminal command and upload recovery

- **Decision**: A deliberate authenticated cancellation write serializes against execution using the existing sorted actor-user lock, held through the short database transaction. For a domain command, return its COMMITTED outcome if execution won; otherwise insert/reuse an append-only CANCELLED marker under the same actor/kind/key. Every executor checks that terminal row before effects. A late request using a CANCELLED key returns 409/COMMAND_CANCELLED for any payload. GET remains observational: NOT_OBSERVED is nonterminal and never releases a guard.
- **Upload decision**: Owner/purpose/upload-key uniqueness and the same actor/asset lock ordering protect registration, cancellation and READY completion. Absent intake may insert a minimal FAILED/UPLOAD_CANCELLED ImageAsset marker with null file/hash/upload-time facts; STAGING cancellation fences the processing lease and preserves already captured immutable facts. READY/DELETING/DELETED returns the accepted asset's truthful availability; cancellation cannot delete or unaccept it. External parser/child/file cleanup happens after the fence, holding capacity until cleanup finishes. Late registration, processing and restart cannot revive FAILED.
- **Authority and recovery**: Cancellation requires the caller's current active verified role/session and own identity; it does not require paid/task eligibility merely to fence unused work. Committed/private outcome disclosure still uses current resource authorization. A lost cancellation reply observes or deliberately repeats the same idempotent cancellation, never a new business intent. Only a validated committed/failed/cancelled result can retire the associated guard; NOT_OBSERVED, timeout, a nondurable rejection or local dialog reset cannot. Before dispatch, client validation may release a never-dispatched local handle. After a confirmed unused-key fence, refresh current resource/eligibility, preserve permitted drafts, and require a deliberate reconfirmed new command/file selection with a new key. Cancellation cannot reverse a committed review or extend the original task cutoff.
- **Rationale**: Both execution and cancellation lock the actor before checking the unique terminal identity, so exactly one can win across connections or a delayed request. Reuse `lockIdentityUsers` and ledger participant locking rather than introduce another locking or command platform. Cancellation contains no pretend target/hash when the original request was never received. Concrete states/routes and race tests are in the data model, HTTP/UI contracts and quickstart.

## Codes and successful usage

- **Decision**: Normalize surrounding whitespace and uppercase once in shared contracts; store globally unique retained normalized text and an immutable associated task. Persist one unlock per employee/task/date and count only accepted unlocks.
- **Rationale**: The owner explicitly rejected cross-task normalized reuse, including paused codes. Pausing and new unlock take the same code/task locks. A retained unlock is checked before deciding whether a new enabled code is needed, so pause blocks only new unlocks. Different codes/replays do not inflate successful usage. Codes do not confer subscription entitlement or another daily claim.
- **Alternatives considered**: Per-task uniqueness, case-sensitive lookup, releasing paused text, use caps and independent code expiry contradict or expand the clarified scope.

## Multipart and raster dependencies

- **Decision**: Propose direct API dependencies `@fastify/busboy` 3.2.2 and `sharp` 0.35.5 only when P05 implementation adds the pipeline. Use a request-local multipart stream and disposable decoder child. Preserve the existing Next transitive sharp 0.34.5 and all unrelated locked packages.
- **Rationale**: Current API manifests have neither dependency. The selected multipart parser has bundled TypeScript definitions and no runtime framework dependency; it can enforce byte/part/header bounds directly. Sharp's current supported release accepts Node >=20.9, compatible with the locked Node 24; its tagged source/API supports the required decode restrictions and re-encoding. Version/API facts were checked against primary package metadata/tagged source and [Busboy documentation](https://github.com/fastify/busboy/tree/v3.2.2), [Sharp input options](https://sharp.pixelplumbing.com/api-constructor/), [Sharp utilities](https://sharp.pixelplumbing.com/api-utility/) and [security policy](https://github.com/lovell/sharp/security/policy). Reverify advisories/platform binaries during installation; no install or lockfile edit occurs in PLAN.
- **Alternatives considered**: Multer is a viable Express wrapper, but adds conventions/dependencies when this boundary already needs direct streaming control. Memory buffering every upload, signature-only checks and importing Next's transitive image dependency into API are unsuitable. Another image library/antivirus service or object-store product is not needed for the accepted local-raster MVP.

## Finite upload and processing limits

These are technical safety budgets, not commercial entitlement limits. The original-file bound must agree across server, shared upload contract and accepted UI hints. The separate aggregate multipart bound governs request streaming and future ingress.

| Boundary        | Chosen limit                                                                                                                                                                                                                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Original file   | 1 file, 1..5,242,880 bytes inclusive; PNG/JPEG/WebP only                                                                                                                                                                                                      |
| Multipart       | exactly `file` plus `commandId`; files 1, fields 1, parts 2; explicitly validate field names <=32 bytes and field values <=128 bytes; parser header work bounds 8 pairs/8,192 bytes                                                                           |
| Request body    | 5,259,264 bytes total, including multipart overhead; Content-Encoding identity; boundary 1..70 characters                                                                                                                                                     |
| Decoded raster  | width/height each <=8,192; total <=16,777,216 pixels; <=4 channels; exactly one frame; reject animated/multipage input                                                                                                                                        |
| Stored output   | stripped, oriented canonical PNG; 1..33,554,432 bytes; reject over-limit output without READY asset                                                                                                                                                           |
| Decoder         | Sharp strict decode failure, bounded input pixels/channels, unlimited disabled, sequential read, concurrency 1, cache disabled; 5-second library timeout                                                                                                      |
| Process         | disposable child; 128 MiB JavaScript heap budget; 10-second whole-process wall deadline with forced termination/reaping                                                                                                                                       |
| Concurrent work | 2 admitted uploads/decoders per API process; reject excess with retryable busy response, no unbounded queue                                                                                                                                                   |
| Staging         | reserve at most 40 MiB per admitted upload, 80 MiB active reservations; cap aggregate temporary files/reservations including crash leftovers at 256 MiB for the initial single-process root; refuse admission/exhaustion until reconciliation restores budget |
| Upload lifetime | total multipart input deadline <=30,000 ms, shortened by a stricter existing request deadline; cancel stalled/disconnected streams independently of decoder timeout                                                                                           |
| Maintenance     | at most 100 assets per scan, one scan each 60 seconds, lease 120 seconds; unfinished STAGING age-out after 1 hour                                                                                                                                             |

- **Decision**: MIME, safe filename/extension when present, signature and the actual decoded allowlisted format must agree. Reject traversal/control filenames rather than silently sanitizing them; server-generated opaque storage keys are the only path inputs. Do not load active/unsupported image formats even to convert them. Re-encoding strips metadata and does not expose original bytes.
- **Rationale**: Application handlers must reject unknown/duplicate/truncated parts and literal-field violations. The selected parser does not implement multipart `fieldNameSize`; its header-count/byte options bound parsing rather than automatically reject excess headers. Verify these actual behaviors, not assumed option semantics. Stream-count canonical output and abort above its cap before exhausting staging reservations. The multipart deadline bounds stalled input; pixel/dimension/channel/frame/output budgets, two slots and a killed/reaped child bound decode work. Detect APNG animation with bounded PNG container validation or verified decoder behavior, not an assumed metadata-page count. Node's heap flag is not a native RSS guarantee; measured hostile tests must fail Gate B for observed exhaustion, and P11 enforces production memory/CPU/volume limits. The [OWASP file-upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) supports validation, isolated storage and constrained processing.
- **Alternatives considered**: Extension/MIME alone, accepting SVG/GIF, processing in the public request process without an enforced wall deadline, unbounded waiting work and output resizing that silently changes accepted evidence safety are rejected.

### Native-resource acceptance for Gate B

Chosen local evidence ceilings are 536,870,912 bytes (512 MiB) per decoder child's RSS, 1,073,741,824 bytes (1,024 MiB) for the sum of two children's retained high-water observations, and 134,217,728 bytes (128 MiB) sampled API RSS growth over its warmed idle baseline. These are proposed empirical acceptance budgets, not measured results or OS-enforced guarantees. The maximum four-channel raster is 64 MiB; the child ceiling allows its 128 MiB JavaScript heap plus multiple native raster/encoder working buffers and library overhead. If valid required fixtures cannot meet these ceilings, Gate B fails and the owning design must be reviewed; do not silently increase limits.

Use numeric-only `process.memoryUsage.rss()` observations in bytes at 100 ms intervals and before/after decoding; normally completing children send and acknowledge a final `process.resourceUsage().maxRSS * 1024` value before exit. Node documents maxRSS in KiB and RSS as including JavaScript/native allocations ([Node 24 RSS](https://nodejs.org/docs/latest-v24.x/api/process.html#processmemoryusagerss), [resource usage](https://nodejs.org/docs/latest-v24.x/api/process.html#processresourceusage)). Retain maxima per actual child identity. The parent independently measures its API RSS and watches child close/termination. Measure an isolated API process after initialization with no outstanding work; fixture generation/test-runner/browser allocations do not belong to that baseline. Sampling does not detect every transient peak or impose a hard cap. Abrupt termination records partial observations and its exit/kill outcome truthfully; it cannot claim a final high-water reading. Missing normal-completion metrics or an invalid/mismatched metric fails resource acceptance.

The deterministic synthetic corpus and two-slot workload in [quickstart](quickstart.md#native-resource-acceptance-workload) must satisfy the ceilings with finite deadlines/storage and cleanup. Any observed ceiling breach, unexpected native allocation failure, OS OOM or unexpected decoder crash fails B; a deliberate kill/stall case instead proves supervision/cleanup and must be identified separately. Reject excess admission before a third decoder starts. P11 still owns production OS/container memory/CPU/volume/backup enforcement.

## Database/filesystem recovery and retention

- **Decision**: Use purpose-bound `ImageAsset` rows with durable upload identity/hash and lifecycle `STAGING -> READY | FAILED`, then `READY -> DELETING -> DELETED`. Write/validate/sync a canonical file and atomically rename within the storage filesystem before the READY database commit. Observe upload commands as PENDING/READY/FAILED; never return a usable asset before READY. Recoverable staging and deletion scans are owned by API lifecycle, with no Redis/worker platform.
- **Rationale**: DB and local files cannot share a transaction. Durable state covers crashes between staging/rename/READY, lost READY replies and unlink/DELETED. The completed input-upload time starts each accepted file's retention age; retain it through processing/replacement and do not reset it. Invalid unfinished temporary files are not accepted proofs. All accepted READY proofs, even unattached or superseded, keep at least 30 complete 24-hour periods. Every evidence version associated with any pending submission is exempt, not just its latest pointer. Cleanup locks assets, reads pending-reference predicates and conditionally fences them as DELETING; attachment/replacement locks the same assets and permits only READY. Cleanup never takes user/task/submission locks after asset locks. Serializable retry/predicate validation protects reference races. Unlink happens outside transactions and resumes under a durable lease.
- **Alternatives considered**: Deleting old current-pointer-only evidence, eagerly deleting a failed replacement's old proof or orphan files under 30 days, holding a transaction across I/O and using a timer without durable leases violate recovery/retention. A universal job/outbox system is not necessary for bounded storage maintenance.

## Purpose and private-read boundaries

- **Decision**: Proofs and administrator task illustrations use separate upload/metadata/content routes and a checked asset purpose. Both remain outside `public` and static serving. Employee proof reads authorize current owner or current ADMIN; paid/task eligibility applies to new work, not inspection of already accepted own work. Illustration reads authorize admins or employees with permitted access to its task. No remote URL import or server-side task-link fetch.
- **Rationale**: Current active Free/expired/task-restricted owners may inspect their own accepted history; banned/revoked accounts remain denied. Admin review after an employee ban does not grant that employee access. Explicit blob reads through central bearer transport create temporary account/resource-owned object URLs; direct image tags do not send its memory bearer token. Private responses use no-store, no-sniff and fixed raster headers. The installed Next Image docs warn that the default optimizer does not forward authorization headers, so it must not proxy private proofs.
- **Alternatives considered**: Public proof URLs, public optimized-image caches, client paths/remote URLs, sharing illustration/proof authority and storing private bytes in Query data are rejected.

## Frozen UI integration and verification

- **Decision**: After Gate B, wire the nine existing routes with shared contracts, employee/admin feature adapters/hooks, the established transport and query runtime. Keep bounded C1/C2 changes and all other approved presentation. Reuse existing confirmations, review preview and pagination controls; retain other domains' fixture providers.
- **Rationale**: P03/P04 already provide admin login, session guards, `financial-query.ts`, `financial-response.ts`, private command ownership patterns and Playwright 1.63.0. The financial query helper currently hardcodes `p04`, so P05 requires a narrow namespace/lifecycle extension, not an assumed generic helper. `AdminImageUpload` currently emits blob URLs and permits SVG; its sole task-form consumer needs a real File and temporary preview. Employee task code gating imports admin fixture authority and can fail open; remove that P05 dependency. Current single-proof review popup needs its own focus lifecycle within the existing surface. Gate B must prove actual files/PostgreSQL/time/races; Gate F requires authenticated app/browser results and affected P01-P04 regressions. P05 is not a full-roadmap regression checkpoint.
- **Alternatives considered**: Replacing route/layouts, adding a design system, global fixture-provider removal, another Axios/Query client, optimistic reward credit or fixture fallback expands scope or fabricates authority.
