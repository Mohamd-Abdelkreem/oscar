### User Story 1 - Submit One Eligible Daily Task (Priority: P1)

An eligible employee sees the server's current daily opportunity, unlocks it when required, uploads a screenshot and declares execution. The accepted work is pending review and preserves its reward without becoming spendable money.

**Why this priority**: This captures the daily entitlement safely and prevents local state, upgrades or another device creating extra claims.

**Independent Test**: With the existing identity/subscription/calendar foundations and a published task, exercise submission at fixed Baghdad times using separate employees/devices and inspect the saved claim, declaration, reward and unchanged wallet. Interface checks additionally require Gate B and compliance with accepted C1/C2 boundaries.

**Acceptance Scenarios**:

1. **Given** an active paid, unrestricted employee on a weekday before 12:00 Baghdad, **When** they inspect or attempt work, **Then** the opportunity is upcoming and new unlock/submission is denied; exactly 12:00 opens it, exactly 18:00 closes it, and Saturday/Sunday never provide a task opportunity.
2. **Given** an anonymous, unverified, Free, expired, banned or task-restricted employee, **When** they attempt a protected work action directly, **Then** it is denied without a claim, unlock or credit. A withdrawal-only restriction does not itself prohibit otherwise eligible task work.
3. **Given** a gated open task, **When** the employee supplies an incorrect, unrelated or paused code, **Then** no unlock/usage/claim is accepted; an enabled code associated with that task creates one employee/task/date unlock and records its successful use time.
4. **Given** a successful unlock, **When** the code is later paused, **Then** that unlock remains valid within the original task window and normal account eligibility, while employees without an unlock cannot unlock through the paused code.
5. **Given** eligible open work, **When** a submission lacks an affirmative declaration, references another employee's asset, uses an unready/wrong-purpose asset or forges reward/subscription/date fields, **Then** it is rejected without claiming the day or changing funds. Opening an external link alone is not a declaration or a submission.
6. **Given** valid owned proof and declaration under S1, **When** submission is accepted, **Then** one pending claim captures the active subscription and 2 USDT reward, proof and original deadline; available, reserved and referral funds remain unchanged.
7. **Given** a same-date accepted claim, **When** the employee upgrades, switches devices or retries with another task/subscription/request identity, **Then** no second submission or reward entitlement is created for that employee and Baghdad date; rejected work also consumes that date's accepted claim.
8. **Given** two simultaneous submission attempts, or a successful submission whose response is lost, **When** the employee reconciles their day, **Then** exactly one saved claim is found and no credit is guessed, duplicated or automatically retried as new work.
9. **Given** an employee viewed/unlocked a task before its instructions or target link changed, **When** they attempt their first submission against that older revision, **Then** it conflicts without consuming the daily claim or changing funds; they must refresh and perform work matching the current instructions before resubmitting within the open window.

### User Story 2 - Make One Final Review and Credit the Captured Reward (Priority: P1)

An authorized administrator examines private evidence and the execution declaration, then confirms approval or reasoned rejection. Approval posts the captured reward once; either decision is final and remains explainable.

**Why this priority**: Review is the sole reward-credit boundary, so replay, stale evidence and partial writes must not alter employee money.

**Independent Test**: Prepare valid pending submissions, perform competing decisions using separate authenticated administrators/connections and inspect final status, evidence reference, reward posting, wallet and audit. Reuse recorded employee terms rather than current package prices.

**Acceptance Scenarios**:

1. **Given** pending S1 work captured at 2 USDT, **When** it is approved after an upgrade to O1, package edits, subscription expiry or a later employee ban, **Then** exactly 2 USDT is added once as an available non-referral task reward. The ban still blocks employee login/withdrawals.
2. **Given** a pending submission, **When** approval commits, **Then** approval status, one reward credit, ledger/source totals and required audit become visible together. A controlled failure before completion leaves all those effects unchanged.
3. **Given** two approvals, repeated delivery or a new request key for the same submission, **When** they complete, **Then** there is one final approval and one captured-reward posting. A same-key request with different decision/reason/target input conflicts without additional effects.
4. **Given** competing approval and rejection, **When** both attempt the same pending submission, **Then** one final decision wins, the other reports the saved result or conflict, and credit occurs only if approval won.
5. **Given** pending work, **When** rejection with the required reason is confirmed, **Then** it becomes finally rejected with zero reward credit, zero deduction and no reversal posting. It cannot be edited, resubmitted or approved later.
6. **Given** finally approved work, **When** any administrator requests rejection, reversal, evidence change or reward change, **Then** the final outcome and money remain unchanged.
7. **Given** evidence replacement or a task/account change raced with review, **When** the administrator confirms a decision, **Then** the decision binds to the current reviewed evidence and accepted terms; an obsolete evidence version cannot silently approve a different screenshot.
8. **Given** missing/currently revoked admin authority, an employee role, missing required reason or an uncertain review response, **When** review is attempted or reconciled, **Then** unauthorized/invalid decisions have no effects and uncertainty resolves from the saved submission instead of a fabricated success or another reward attempt.

### User Story 3 - Keep Proofs Private, Replaceable While Pending and Retained (Priority: P1)

Employees submit actual validated screenshot files and can replace pending evidence before its original cutoff. Only the owner and authorized reviewers can read it, and cleanup preserves reviewable work and history.

**Why this priority**: Proofs are sensitive untrusted files and are needed to justify final financial decisions.

**Independent Test**: Use actual isolated file storage, valid and hostile files, separate employee/admin identities and a controlled clock; inspect access, accepted evidence, cleanup results and retained metadata.

**Acceptance Scenarios**:

1. **Given** a valid decodable PNG, JPEG or WebP at the accepted byte/resource limits, **When** an eligible employee uploads it, **Then** a ready owner-bound proof identifier is returned; a temporary browser preview is not the saved asset.
2. **Given** a file above 5 MB, mismatched content/type, malformed image, active format, traversal name or excessive decoded dimensions/resource demand, **When** it is uploaded, **Then** no usable proof is accepted and the request cannot expose or overwrite another file.
3. **Given** an existing proof, **When** an anonymous caller, another employee, a deactivated/revoked admin or a public/static URL tries to read it, **Then** neither file nor private metadata is exposed. The owner and currently authorized reviewer can read allowed evidence without receiving internal storage paths.
4. **Given** pending work and current permitted employee authority before its captured 18:00 cutoff, **When** its screenshot is replaced with another ready owned proof, **Then** the existing claim keeps its reward, subscription, declaration and original deadline; there is no new claim or credit.
5. **Given** the original cutoff is reached or review is final, **When** replacement is attempted, **Then** it is rejected even if a code, task or subscription later changes. A failed replacement leaves the previously accepted proof intact.
6. **Given** a pending-review proof uploaded more than 30 days ago, **When** cleanup runs, **Then** it remains readable for review. A proof referenced by a pending submission cannot be deleted during an overlapping cleanup/review/replacement operation.
7. **Given** a final submission's proof younger than 30 days, **When** cleanup runs, **Then** it is retained; after 30 complete days from that proof's upload it may be removed, while submission, declaration, decision, financial and audit metadata remain. Replacement does not reset another file's upload age.
8. **Given** storage exhaustion, processing failure, interrupted upload or a missing retained file, **When** upload/read/replacement is attempted, **Then** the result is truthful and recoverable, no phantom proof/claim/credit is produced and no pending evidence is discarded to hide the failure.

### User Story 4 - Publish the Common Daily Task and Manage Associated Codes (Priority: P2)

An administrator manages task content, one publication date, link/image and code gating, and inspects successful code usage by employee and time. Changes affect eligible future work while preserving accepted submissions.

**Why this priority**: Operators need a real daily opportunity and auditable access without accidentally introducing new entitlement or rewriting history.

**Independent Test**: Create and inspect tasks/codes using current admin authority, control the business date and pause state, and verify employee availability and retained successful usage/submissions after edits and reload.

**Acceptance Scenarios**:

1. **Given** an authorized administrator, **When** valid task content, Baghdad publication date, external link, optional image and gating are saved, **Then** the common opportunity persists and is eligible only during that date's fixed weekday window; a browser clock or editable demo time cannot change it.
2. **Given** no published opportunity, a weekend publication or a second competing daily publication, **When** an employee reads the day or an admin tries to publish, **Then** no invented task/reward is offered and the one-common-opportunity/weekday policy is enforced.
3. **Given** accepted submissions, **When** task content, image, publication state or gating is changed or a referenced task/code is removed from active use, **Then** existing claims, reviewed evidence, unlock/usage history, captured deadlines/rewards and final decisions remain attributable and cannot be erased or rewritten.
4. **Given** a code associated with one task, **When** it is created enabled or paused and later enabled/paused, **Then** current status persists, changes are audited, and it grants no cross-task or additional daily claim. Creating the same normalized text for another task, including when the existing code is paused, MUST conflict without creating a code; lowercase or surrounding whitespace cannot bypass this uniqueness.
5. **Given** a successful code unlock is retried or raced, **When** usage is inspected, **Then** one employee/task/date successful unlock is shown with server time; invalid attempts do not appear as successful usages and repeated use does not inflate successful employee counts.
6. **Given** two administrators edit the same task/code from stale views, **When** the later command is applied, **Then** it cannot silently overwrite newer state or accepted work; the affected administrator receives a truthful conflict and can reconcile.
7. **Given** task/code/submission lists with filters and multiple pages, **When** an authorized admin searches or navigates, **Then** current bounded results, counts and stable order reflect those filters without exposing another audience's private data or truncating history silently.
8. **Given** a task with a successful unlock or accepted submission, **When** an admin attempts to change its publication date, **Then** the change conflicts without moving that opportunity, its unlocks or claims; another date requires a new task. A date-edit/first-participation race MUST either move an unclaimed/unlocked task before participation is accepted or accept participation and deny the date change.

### Edge Cases

- Baghdad weekday/date boundaries and the exclusive 18:00 cutoff apply to unlocks, submission and replacement even when the browser/host clock disagrees or an upload began earlier; acceptance time determines whether work may commit.
- No published task, paused publication, ungated work, invalid/wrong-task codes and pause-versus-unlock races cannot manufacture an opportunity or revoke an already accepted claim. An unlock alone does not consume or reward the daily claim.
- Subscription upgrade-versus-submission must capture one effective entitlement; later package edits, expiry, restrictions or bans cannot reinterpret a valid saved reward. New work still needs current authority.
- Duplicate claims across dates/tasks/subscriptions/devices, repeated successful unlock delivery and same-key/different-payload requests must preserve distinct permitted identities and reject conflicts.
- Approval-versus-rejection, simultaneous approvals, replacement-versus-review and cleanup-versus-pending references must end in one explainable state with no duplicate credit or evidence deletion during review.
- Instructions/link edits racing a first submission must accept the current revision or reject stale work without consuming the daily claim. Date edits racing the first successful unlock/submission cannot move an opportunity after participation is accepted; a new task for another date must use its own globally unique codes.
- Filename traversal, spoofed MIME/extension, GIF/SVG/arbitrary content, decompression bombs, oversized parts and hostile dimensions are rejected at the real proof-upload boundary; normal JSON body limits are insufficient evidence.
- Upload or storage failure, unattached ready uploads, superseded proof files, inaccessible retained evidence and interrupted cleanup need bounded cleanup/recovery without claiming submission success or erasing required metadata.
- Lost success responses and session changes require reading the durable existing operation; no automatic financial replay, fixture fallback or assumed reversal is permitted.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: The system MUST deliver both P05 groups under this one feature, enforcing Gate B before frontend integration and Gate F before P05 completion. Presentation work MUST stay within accepted C1/C2 boundaries and the remaining frontend freeze.
- **FR-002**: Every protected task/code/proof/submission/review action and private-file read MUST enforce current authenticated identity, role, status, session authority, resource ownership and applicable restrictions. Changes that race a command MUST be rechecked before its consequential write; hidden controls do not grant authority.
- **FR-003**: Employee work actions MUST require a current active verified account, effective paid subscription and no task restriction/full ban. Free/expired accounts cannot create new work; a withdrawal-only restriction MUST NOT independently prohibit eligible task work. Previously valid work remains reviewable under FR-022.
- **FR-004**: The system MUST determine task date, opening, closing and availability on the server using `Asia/Baghdad`: Monday-Friday, 12:00 inclusive to 18:00 exclusive. Saturday/Sunday MUST show holiday availability without an opportunity; host/browser time cannot override the rule.
- **FR-005**: Authorized administrators MUST manage task description/instructions, one Baghdad publication date, external link, optional illustration, publication state and code gating. There MUST be at most one common daily opportunity per date. The publication date MAY change only before the first successful employee unlock or accepted submission; afterward it MUST remain fixed and another date requires a new task. A date-edit/first-participation race MUST enforce that rule at acceptance without moving existing unlocks or claims. No publication or a paused opportunity MUST NOT produce an invented task. The fixed window and one-date publication MUST NOT become configurable hours or an unapproved recurring schedule through existing form inputs.
- **FR-006**: Task links MUST be validated safe web links and task illustrations MUST be validated bounded images. Employee proof identifiers MUST NOT be accepted as public task illustrations, nor illustration identifiers as employee proof. Opening a link alone MUST NOT prove execution. No arbitrary URL/file import or active upload may bypass file safety or private access.
- **FR-007**: Task/publication edits MUST preserve accepted daily claims, captured task instructions/link, terms/deadlines, evidence, successful unlock attribution and final decisions. Changes to active content MUST be auditable; referenced task/code removal or pause MUST NOT cascade-delete accepted work or grant a second claim. Instructions/link edits MAY occur during the open window, but first submissions MUST identify and match the current task revision. A stale revision MUST conflict before a daily claim is accepted, consume no claim and change no funds; the employee MUST refresh and perform work matching the current instructions within the existing window.
- **FR-008**: Authorized administrators MUST create codes associated with a task and enable/pause them. Code text MUST be normalized by trimming surrounding whitespace and converting letters to uppercase, matching the existing entry behavior. That normalized text MUST be globally unique across all retained codes, including paused codes; different tasks MUST NOT reuse it. Duplicate/conflicting creation MUST NOT create another code or ambiguous unlock authority. This phase MUST NOT invent code-use caps or independent expiry.
- **FR-009**: A gated task MUST require an enabled valid associated code for a new employee/task/date unlock, current account eligibility and an open task window. Ungated work MUST NOT require a code. Invalid/wrong-task/paused codes and missing fixture providers MUST fail closed without a successful usage record.
- **FR-010**: A successful unlock MUST persist employee, task, code, business date and server acceptance time exactly once for that employee/task/date. Retries or another code for the already unlocked opportunity MUST NOT create extra successful usages, claims or rewards.
- **FR-011**: Pausing a code MUST block new unlocks while preserving existing accepted unlocks, subject to the task window and normal account eligibility. A pause/unlock race MUST have an authoritative ordered outcome rather than accepting an unlock from stale status.
- **FR-012**: Administrative code lists/details MUST show actual status, successful usage counts and associated accounts/times, distinguish submission status from unlock, and exclude invalid attempts from successful usage. Employee results MUST NOT disclose other users' usage or a demo/admin code as unlock authority.
