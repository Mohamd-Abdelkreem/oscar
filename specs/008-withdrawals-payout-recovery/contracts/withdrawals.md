# P08 Proposed Withdrawal HTTP Contract

This is a design contract for future implementation, not a route inventory or executed acceptance. It covers Group A and the safe public facts added by Group B. See the [spec](../spec.md), [research](../research.md), [data model](../data-model.md) and [runtime contract](payout-runtime.md). No frontend integration is authorized by this artifact.

## Owners and transport

Proposed browser-safe schemas belong in `packages/contracts/src/withdrawals/withdrawal.schema.ts`, with explicit exports from the existing `packages/contracts/src/index.ts`. Proposed routes, controllers, DTO aliases, services, queries and mappers belong in `apps/api/src/modules/withdrawals/`; the existing `apps/api/src/router.ts` composes them. Preserve package names and the established `ResponseHelper`, validation middleware and OpenAPI construction.

All paths below are relative to the configured API prefix, currently `/api/v1`. Responses use the existing JSON success/error envelopes and `Cache-Control: no-store`; domain `data` has its own strict shared Zod schema. The success envelope alone does not validate domain facts. Unknown command fields, including submitted owner, fee, eligibility, deadline, role, status and transaction outcome, are rejected. Controllers receive parsed input and current authenticated session context, never substitute a client actor or missing context.

Employee routes require current active, verified `USER` authority, session authority and resource ownership. Every POST also uses existing CSRF protection. A task-only block does not block withdrawals. A ban or withdrawal block prevents initiation and claims; a withdrawal-only block permits otherwise authorized destination/request/history reads. All changing authority is rechecked at the transactional boundary. ADMIN routes require current active, verified administrator/session authority; employee IDs in filters do not grant permission. Missing and another employee's resources both return 404 on employee resource reads.

Reuse the current financial amount, instant, source, request-key and counted-hours schemas. Wire amounts are canonical decimal strings with at most six fractional digits: `"100"`, `"21"`, `"79"`; floats, exponent notation, leading zeros, trailing fractional zeros and negative values are rejected. Internal calculations use bounded bigint micro-USDT. Instants are normalized UTC ISO strings. Rates are integer basis points; `fee = floor(grossUnits * feeBps / 10000)`, `net = gross - fee`, with positive net. Company network/resource costs never appear as an employee deduction.

## Employee commands and reads

| Method and relative path                         | Strict input                                             | Success data and status                                                                      |
| ------------------------------------------------ | -------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| GET `/withdrawals/me/destination`                | No query/body fields                                     | 200 destination readiness and `serverNow`                                                    |
| POST `/withdrawals/me/destination/confirmations` | `{ address }`                                            | 201 committed current pending proof state plus delivery outcome; never the token             |
| POST `/withdrawals/me/destination/resend`        | `{ expectedVersion }` for the current pending proof      | 200 newly committed pending proof generation and delivery outcome for its same exact address |
| POST `/withdrawals/me/destination/consume`       | `{ token }`, opaque bounded proof credential             | 200 saved destination state                                                                  |
| POST `/withdrawals/quotes`                       | `{ gross }`                                              | 201 quote and server preview; no reservation                                                 |
| GET `/withdrawals/quotes/:quoteId/outcome`       | UUID path parameter only                                 | 200 quote acceptance outcome                                                                 |
| POST `/withdrawals`                              | `{ quoteId, confirmed: true }`                           | 201 `{ withdrawal, replayed: false }` or 200 replay `{ withdrawal, replayed: true }`         |
| GET `/withdrawals`                               | Existing bounded page query, optional valid state filter | 200 bounded own history                                                                      |
| GET `/withdrawals/:withdrawalId`                 | UUID path parameter only                                 | 200 own saved request detail                                                                 |

Destination readiness is a strict discriminated union. `UNSET` has neither saved nor pending address. `PENDING` carries exact candidate address, proof version, issued/expiry/resend-eligible instants, derived `PENDING` or `EXPIRED` proof status and bounded delivery status (`NOT_ATTEMPTED`, `UNKNOWN`, `ACKNOWLEDGED`, `REJECTED`). `CONFIRMED` carries exact saved address, positive destination version and saved instant; pending authority is absent. All branches carry server time. No branch returns hashes, raw credentials, email URLs or recovery/storage facts.

The shared address shape reuses the existing TRON Base58 shape; the server also validates checksum with the installed protected TRON address primitive before accepting issuance. Address strings are exact validated values, not silently corrected text. Confirmation tokens are 32 random bytes encoded as bounded opaque text; only their dedicated purpose/employee/address/generation-bound hash is persisted.

Proof lifetime uses validated configuration from 60 through 3600 seconds, initially 1800 seconds (30 minutes). Resend cooldown uses validated configuration from 1 through 3600 seconds, initially 60 seconds. Accepted issuance persists expiry and next-issuance instants from those settings, unchanged by later configuration edits. Both new issuance and resend use the cooldown. Rejected validation, stale version, cooldown or authority attempts leave current proof authority unchanged. Accepted issuance/resend supersedes all older unconsumed authority and appends its internal `WithdrawalDestinationAudit` issuance event in the same transaction before email I/O; audit failure rolls back supersession. A late delivery acknowledgement may update only its matching generation. Rejected or uncertain delivery retains the newly committed proof and never restores the old one. Provider acknowledgement means provider acceptance, not mailbox delivery. A committed proof issuance therefore returns its truthful saved state even when delivery is rejected/unknown; no rollback-shaped success or fabricated email delivery is allowed. Existing process-local limiter factories bound issuance/consumption in addition to database cooldown/serialization; they are not claimed to coordinate API processes.

Consumption locks and rechecks current session/account, purpose, user, exact address, latest proof generation and exclusive expiry; it atomically saves the first destination, clears pending authority and appends one matching consumption event. An audit-write failure rolls back the save/clear; rejected or replayed consumption adds no event. These internal events expose no token/hash/full URL or new public history surface. It issues no withdrawal or reservation. Replayed consumption fails with the same safe invalid-proof code; a GET observes the saved winner after a lost reply. Once saved, employee issuance/resend/consume cannot replace it. P10 owns any administrator replacement endpoint.

The proposed email link targets the existing same-origin `/employee/account` route with the opaque token in its fragment. It is not the auth email-verification route, and opening it performs no write. P09 must resolve/wire its pending/result surface and remove the fragment before telemetry or retained client state. P08 must not add a page, popup, hidden success or frontend token handling. Full links and tokens are excluded from logs, request-body diagnostics and ordinary email previews.

## Quotes, acceptance and history facts

A quote contains `quoteId`, quoted/expiry/server instants, gross, fee basis/rate/fee/net, current inclusive min/max gross, confirmed recipient/version, effective membership basis and relevant saved subscription identity/expiry, eligible unreserved NON_REFERRAL/REFERRAL breakdown, candidate `fundedAllocation`, `requiredTopUp`, `canAccept`, safe `blockReason`, and preview initial counted deadline/normalized dispatch time. Reuse the existing `fundedAllocationSchema` for its referral/nonReferral/total shape: components sum to `min(gross, eligible available)`, and funded total plus required top-up equals gross. It is not the accepted full-gross `sourceAllocationSchema`. Expiry is quote creation plus the validated configured TTL, initially 600 seconds, and later configuration edits do not rewrite an existing quote expiry. A preview is not a reservation or accepted schedule.

Initial configured bounds are 16–500 USDT inclusive and Free/expired fee 2100 bps. Active paid membership uses its saved withdrawal fee snapshot. Available retained referral funds are distinct from newly withdrawal-eligible referral funds; only currently paid membership at exclusive expiry permits their new use. Quote allocation follows NON_REFERRAL then REFERRAL. Insufficient funds produce a nonaccepting quote with partial funded components and exact required top-up, following the current purchase-quote pattern; acceptance is denied until a fresh accepting quote is reviewed. Unsupported gross bounds or zero-net fee terms are rejected without a financial effect. A block must be explained by a safe stable code, never an invented zero balance.

Acceptance captures server time after required financial/authority locks and revalidates destination/version, membership/expiry, restrictions, applicable terms and eligible unreserved source components. Materially changed reviewed facts produce `WITHDRAWAL_QUOTE_STALE`; the server does not silently accept different terms. The confirmed request atomically records its exact gross reservation, original allocation, financial projections/audit, immutable terms/recipient/eligibility and actual 72-counted-hour schedule. Redis enqueue occurs only after commit and cannot change the acceptance outcome.

The optional `Idempotency-Key` header uses the existing `financialRequestKeySchema` (1–128 supported characters). Bind it to current actor, operation and canonical parsed intent; reuse with another payload returns conflict. A permanent unique accepted request per quote and allocation per request prevent another debit/reservation even with a fresh or missing header. Same-intent replay returns the original request result and `replayed: true`, subject to current read authority. An unresolved command returns a truthful conflict/in-progress outcome and must be observed rather than assumed absent. Do not blanket-retry database uniqueness or external sends.

Quote outcome is a strict union: `COMMITTED` carries the original accepted request and matching quote ID; `NOT_OBSERVED` carries the unexpired uncommitted quote; `EXPIRED_UNCOMMITTED` carries the expired uncommitted quote. All carry server time. This endpoint checks durable business identity, not a browser request key, and exposes no other employee's quote. A lost acceptance reply can be observed safely even after quote expiry.

Saved request DTOs expose ID/quote ID, acceptance instant, version/schedule version, state, immutable gross/fee basis/rate/fee/net, original source allocation and recipient/version, original/current counted deadline, normalized earliest dispatch instant, server time/remaining counted hours, safe schedule-action history, terminal time/disposition and safe original transaction/finality facts. Completed data records exact net payout and charged accepted fee summing to gross; safely failed data records gross release and zero charged platform fee without rewriting the immutable accepted fee preview. Company network costs are separate facts where authorized, never an employee charge. Detail may include safe action reason/time/actor projection needed for inspection; exclude internal security notes and unrelated identities.

Read countdowns include exact bounded nonnegative `remainingCountedMilliseconds` integer text and `remainingCountedHours` display text truncated toward zero to at most six fractional digits. Both derive from one shared server counted-duration result and clamp at zero. The positive command-hours schema is unsuitable for zero/display countdowns. Saved deadline and exact server time authorize dispatch, never displayed hours.

States are `SCHEDULED`, `SIGNING`, `SIGNED`, `SUBMITTED`, `UNKNOWN`, `COMPLETED`, `REJECTED`, `CANCELLED`, `FAILED`. The first five all count as active, including a possibly live attempt regardless of a lease timeout. `UNKNOWN` is active reserved uncertainty. Terminal data must agree with settlement or exactly one safe release; no browser status can authorize either. A new request after safe failure uses current eligibility/terms and a new 72-counted-hour schedule; no 24-hour cooldown applies.

History uses existing `boundedPageQueryShape` defaults (page 1, limit 25, maximum 100), safe offset validation, fixed `acceptedAt DESC, id DESC` ordering and strict enum filters. Totals include the filters; zero rows have zero total pages; retain existing `hasPreviousPage = page > 1` semantics. Return `financialPageSchema` data (`items`, `pagination`) and matching envelope pagination metadata through the existing helper. ADMIN list adds only bounded employee UUID, state, inclusive from/exclusive to instants and trimmed bounded search filters needed by existing inspection; no arbitrary sort/SQL fields or unbounded history.

## Administrator scheduled actions

| Method and relative path                           | Strict input                                                 | Result                                      |
| -------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------- |
| GET `/admin/withdrawals`                           | Bounded filters/pagination above                             | 200 authorized minimal request list         |
| GET `/admin/withdrawals/:withdrawalId`             | UUID parameter                                               | 200 authorized request/action detail        |
| POST `/admin/withdrawals/:withdrawalId/extensions` | `{ expectedVersion, countedHours, confirmed: true, reason }` | 200 saved request plus replay flag          |
| POST `/admin/withdrawals/:withdrawalId/rejections` | `{ expectedVersion, confirmed: true, reason }`               | 200 saved rejected request plus replay flag |

Reuse the existing bounded version and `confirmedReasonShape`: nonblank reason maximum 500 characters, server audit actor/time. `countedHours` uses `positiveCountedHoursSchema`, which supports exact fractional durations representable as whole milliseconds; do not invent integer-only restrictions. Extensions add to the existing counted deadline, preserve the original basis, increment versions and normalize dispatch separately. Request version checks and the financial lock boundary prevent a stale edit from overriding a claim or extension. Extension/rejection idempotency follows actor/operation/header/payload binding; persisted command identity prevents duplicate effects when observing the same transition. Conflicting intent never reuses a committed financial result.

Both commands require safely unsent `SCHEDULED` and no possibly live attempt. A resulting counted deadline or normalized dispatch instant outside supported years 1–9999, or a duration that cannot be represented exactly by the shared whole-millisecond helper, is rejected without a partial schedule change. This is a representation bound, not an invented business maximum extension. Rejection releases exactly the saved source allocation once in the same state/ledger/audit transaction. There is no hold, manual-complete, approval or arbitrary-status endpoint. Existing bans/withdrawal blocks and future P10 address replacement invoke the same transaction-client safe-cancellation boundary: cancellation wins before claim and releases once, or claim wins and money stays reserved. They never redirect the accepted recipient. P10 replacement HTTP/UI is outside this contract.

## Observable errors and compatibility gate

Use the existing safe error envelope and actual HTTP exception conventions. Proposed domain codes below must be implemented, documented in OpenAPI and tested together; they are not current runtime claims.

| Status  | Code/condition                                                                                       | Observable rule                                                                                                 |
| ------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 400     | `VALIDATION_ERROR`                                                                                   | Unsupported/malformed fields, money, UUID, version, header or pagination; target-prefixed field paths           |
| 401     | Existing unauthorized/session failures                                                               | Missing/expired/revoked authority; no credential contents                                                       |
| 403     | Existing forbidden plus `WITHDRAWAL_BLOCKED`                                                         | Wrong role/current account or action restriction; task-only block excluded                                      |
| 404     | Existing not-found                                                                                   | Missing/not-owned employee resource indistinguishable                                                           |
| 409     | `WITHDRAWAL_PROOF_INVALID`, `WITHDRAWAL_DESTINATION_FIXED`, `WITHDRAWAL_VERSION_CONFLICT`            | Same invalid-proof result for expired/superseded/replayed/mismatched proofs; no replacement or stale transition |
| 409     | `WITHDRAWAL_QUOTE_STALE`, `WITHDRAWAL_ACTIVE`, `WITHDRAWAL_STATE_CONFLICT`                           | Review again/observe active state; no partial effects                                                           |
| 409     | `LEDGER_INSUFFICIENT_FUNDS`, `LEDGER_AMOUNT_BOUNDS`, `LEDGER_IDENTITY_CONFLICT`, `LEDGER_UNRESOLVED` | Reuse existing financial errors where accurate; no new key bypass                                               |
| 409     | `FINANCIAL_WRITES_FENCED`, `NEW_DISPATCH_PAUSED` where applicable                                    | Existing financial control semantics; no forced retry/send/refund                                               |
| 429     | Existing rate-limit/cooldown exception convention                                                    | Safe retry timing; rejected issuance changes nothing                                                            |
| 503/500 | Existing service-unavailable/internal error                                                          | Safe bounded diagnostics; no DB/provider secrets or fabricated financial outcome                                |

The current wallet contract fixes `withdrawalExecutionReady` to false. Any proposed compatibility change must keep it false until both P08 backend gates and configured runtime admission are satisfied; enabling it must not accidentally activate legacy fixture actions before P09 integration.
