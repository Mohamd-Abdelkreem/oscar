# P04 HTTP Contract

**Status**: Proposed endpoints/schemas; none registered by PLAN. Implement producer, shared runtime schema, adapter and OpenAPI together. All paths are relative to configured API prefix (current default `/api/v1`). Reuse `ResponseHelper`, `successEnvelopeSchema`, `errorEnvelopeSchema` and current validation/auth/CSRF middleware.

**US4 implementation**: T030-T037 register the 13 wallet/ledger/finance and referral/root/member/commission GET routes below, using the existing shared schemas and OpenAPI. Employee scope is derived from current identity; selected employee/root IDs require ADMIN authority. These reads use no-store and a RepeatableRead observation for matching rows/counts/summaries. Frontend integration and gates B/F are still pending. Execution evidence is recorded in [tasks.md](../tasks.md).

**US5 implementation**: The backend registers package PATCH, referral-settings GET/PATCH and actor-scoped configuration-outcome GET with shared validation, current ADMIN/session authority and no-store responses. Writes require CSRF, action limits, confirmation and reason. ReadCommitted actor/session/target locks protect replay-before-version validation and atomic target/audit writes; only the original PATCH can return terminal CONFIGURATION_SUPERSEDED. Absent outcome GET remains NOT_OBSERVED. See [tasks.md](../tasks.md) for executed acceptance evidence; this does not establish gates B/F or frontend integration.

## Common Boundary

Every protected route requires active verified current account and unrevoked/unexpired session. USER is the employee role; ADMIN is configuration/finance/root-search authority. Writes recheck under transactional locks. All reads are no-store and private projections. GET does not purchase or edit. All POST/PATCH commands require existing CSRF protocol and bounded validation/action limits. Well-formed IDs never grant access. Missing/foreign private resource IDs consistently return 404; wrong route role returns 403.

Inputs are strict and reject balances, actor/owner, prices/calculations, sources, sponsor, eligibility/outcome and unsupported fields except the expressly allowed admin configuration fields. UUIDs use existing UUID validation; package code enum is S1/S2/O1/O2/A1. Monetary wire values use existing canonical strings (e.g. `"64.8"`, not `"64.80"`, floats, exponent or grouped text), up to six fractional digits and signed-int64-compatible micro-units. Financial JSON instants use the existing supported ISO/UTC normalization; work dates use businessDateSchema. Counters are bounded positive integers. No persistence bigint is serialized directly.

Success envelope retains success/statusCode/message/data/requestId/timestamp/path and optional paginationMeta. Adapters validate envelope AND endpoint data, resource scope and pagination consistency. Errors retain safe stable code/status/message/field errors; no SQL, secrets, raw request/response or production stack. Lists place `pagination` in data so current ResponseHelper also produces matching paginationMeta; no second envelope.

## Terms and Membership Shapes

`PackageTerms`: code, tierOrder, version, price, dailyReward, countedWorkDates, withdrawalFeeBps, conditionalGross and calendar `{zone:"Asia/Baghdad",workdays:[1,2,3,4,5],firstDateCutoff:"18:00",expiryBoundary:"EXCLUSIVE_NEXT_CALENDAR_DATE_START"}`. Price/reward are positive existing amount strings, duration positive supported integer. conditionalGross is exact reward*duration before cost/fees, conditional on approved eligible tasks; no return/year guarantee. Versions/rates are integers, money never numbers.

`AdminCatalogItem`: `{terms:PackageTerms,activeSubscriptionsCount}`. The count is a nonnegative safe integer, computed by saved package code from subscriptions where state=CURRENT and activationAt<=serverNow<expiresAt. It counts effective paid terms, independent of task/withdrawal restrictions; account restrictions remain separate authority information. Terms, counts and one serverNow share a consistent RepeatableRead observation with current ADMIN/session recheck. Exact expiry must remove a term from the count without waiting for maintenance; an upgrade moves the count from its prior package to the purchased package. Zero is valid only from a successful aggregate. No employee list or fixture count is returned. This live metadata is never part of purchased PackageTerms snapshots.

Supported configuration bounds reuse the current financial/calendar contracts: price and dailyReward are positive canonical amounts no greater than MAX_USDT_AMOUNT (`9223372036854.775807`); withdrawalFeeBps and each of exactly five referral rates are integers 0..10000. Proposed PostgreSQL Int countedWorkDates and counters are integers 1..2147483647. New edits require expectedVersion<=2147483646 so increment cannot wrap; matching committed replay still resolves before fresh-edit validation. Compute conditionalGross in bigint micro-units and require dailyRewardUnits*countedWorkDates<=9223372036854775807. Shared BusinessClock must validate first/final dates and exclusive expiry in supported years 0001..9999, including UTC serialization, at configuration acceptance and again for quotes/purchases. These are representation bounds, not new commercial limits; reject invalid resulting terms rather than clamp, round or overflow.

`Subscription`: id, purchaseId, saved PackageTerms, activationAt, firstWorkDate, finalWorkDate, expiresAt, state CURRENT/REPLACED/EXPIRED. No current catalog recomputation. `Membership`: `{employeeId,serverNow,effective:"FREE"|"PAID",subscription:Subscription|null}`. An expired CURRENT term can remain shown as saved history while effective is FREE; active iff CURRENT and activation<=serverNow<expiry. No guessed FREE on failed read.

## Quote, Command and Reconciliation

`PurchaseQuote`: quoteId, packageCode, action PURCHASE/UPGRADE, terms, quotedAt, quoteExpiresAt, serverNow, previousSubscriptionId nullable, fullDebit, usableFunds, fundedAllocation `{referral,nonReferral,total}`, requiredTopUp, `canPurchase`, `blockReason` nullable, preview `{firstWorkDate,finalWorkDate,expiresAt}`. Block reasons distinguish insufficient funding and transition prohibition; active same/lower-tier quote creation may instead return the documented conflict. Source amounts are unreserved; funded total=min(fullDebit,usableFunds), referral-first, funded total+top-up=fullDebit. Terms/review dates are material. Activation occurs at commitment and is not promised as quotedAt. Internal intent hashes, account snapshots and ancestor private eligibility are omitted.

Initial S1-to-O1 example: fullDebit `"600"`, usableFunds `"40"`, requiredTopUp `"560"`; saved prior price `"60"` yields commission base `"540"` and eligible L1 `"64.8"` at 1200 bps. Both new purchase and upgrade debit full price. Higher tier with equal/lower edited price still upgrades, with commission base zero.

`PurchaseResult`: purchaseId, quoteId, action, purchasedAt, packageCode, fullDebit, full existing sourceAllocation `{referral,nonReferral,gross}`, commissionBase, `subscriptionAtPurchase` (id, purchaseId, saved terms/dates and immutable stateAtPurchase=CURRENT), and `walletAfter` saved event components. It never embeds mutable live subscription state; membership/history reads expose later REPLACED/EXPIRED. Employee result never contains ancestor wallets/credentials/private eligibility; own earned commissions are read separately. This event snapshot cannot replace current wallet cache. `replayed` describes request processing, not a new purchase.

Optional `Idempotency-Key` follows existing financialRequestKeySchema (1..128 permitted characters), actor/operation/intent binding. Purchase business key is persisted quote ID; buyer sequence independently rejects two quotes against one generation. Same key/different quote conflicts; same quote/new or absent key returns the same outcome without award replay. Matching replay still checks current session/ownership and binds/validates incoming alias through the ledger, before returning saved data. Already committed replay bypasses quote TTL/current-terms checks.

`QuoteOutcome`: discriminated COMMITTED `{quoteId,purchase:PurchaseResult,serverNow}`, live NOT_OBSERVED `{quoteId,quote:PurchaseQuote,serverNow}`, or EXPIRED_UNCOMMITTED `{quoteId,quote:PurchaseQuote,serverNow}`. The owned quote must exist. Outcome reads lock the buyer user row using the same lock as purchase, then recheck session and use post-lock ReadCommitted quote/purchase reads and fresh time. An existing purchase wins COMMITTED even after TTL. Live absence is NOT_OBSERVED, not terminal failure or permission for a replacement. Expired absence is EXPIRED_UNCOMMITTED only after this lock barrier: any purchase already holding the lock finished before the read, and a delayed command cannot consume the expired quote because it rechecks current time after the same lock. Lock timeout/failure never returns that terminal state. No quote state, funds or refund is mutated by GET.

Persist/read back an opaque account-scoped quote handle before dispatch and block new intents when one remains after reload/tab change. Reconciliation returns original safe terms for visible review. Explicit same-quote retry of a live outcome is business-safe but never automatic; require original terms and current authority. Once dispatched/uncertain, clear only matching handle after authorized COMMITTED or locked EXPIRED_UNCOMMITTED. A failed retry/reconciliation, live absence, unavailable read or timeout cannot prove an earlier dispatch failed. Local pre-dispatch failure may release a newly claimed handle only if no request for that intent was ever dispatched.

Fresh commitment rejects changed configuration, buyer sequence/membership, disclosed components or recomputed work-date preview. No silent new terms, insufficient-funds debit or optimistic success. The complete transaction either commits or rolls back; transport 5xx/timeout/cancel/malformed success does not prove which observation reached the client.

## Configuration Commands

`PackageEdit`: commandId UUID, expectedVersion, confirmed:true, reason 1..500 non-whitespace characters and at least one of price/dailyReward/countedWorkDates/withdrawalFeeBps. Omitted fields are unchanged; null/blank/unknown fields rejected. Canonical positive amount strings; duration supported positive integer with exact conditional-gross/calendar bounds; fee uses existing bps validation. Codes/tierOrder/calendar semantics cannot be patched.

`ReferralEdit`: commandId, expectedVersion, confirmed:true, reason and exactly five ratesBps integers in fixed L1-L5 order. No compression/backfill option. General settings UI remains later scope.

`ConfigurationResult`: changeId, commandId, target `{kind,packageCode?}`, occurredAt, expectedVersion, committedVersion, reason, saved before/after allowed terms and replayed. Actor is server-derived; response may include authorized actor ID/display name, never submitted identity. Matching actor/command intent returns saved change; changed intent conflicts. Different commands against one expected version cannot both update. No version wrap/reset.

`ConfigurationOutcome`: COMMITTED with saved change or NOT_OBSERVED with commandId/serverNow, scoped to current admin actor; no record is not proof an earlier request cannot commit. After uncertain save, preserve draft and reconcile original command before permitting replacement. Re-read current configuration before editing again; historical after-snapshot is not today's counter.

An explicit user-confirmed retry uses the exact original command UUID, target, expectedVersion, allowed fields, reason and confirmation; the focused UI owner retains this frozen intent across dialog close/remount. It never substitutes current fields/version or a fresh UUID. Under compatible ordered actor/session and target locks, configuration writes use fresh post-lock ReadCommitted observations, recheck current authority and look up the actor/command first. Matching saved intent returns the committed result before any current-version validation; changed saved intent conflicts. With no saved command, currentVersion=expectedVersion permits the original atomic edit; currentVersion>expectedVersion returns proposed 409 CONFIGURATION_SUPERSEDED. That response is terminal for this matching original intent because every delayed request rechecks the same locked target and conditional expected version, and counters never decrease. currentVersion<expectedVersion remains CONFIGURATION_STALE, not terminal evidence. Lock/read failure, conflict exhaustion, NOT_OBSERVED, transport failure and generic denial/error cannot prove that an earlier request will not commit.

Clear a dispatched configuration guard only after a validated matching COMMITTED result or CONFIGURATION_SUPERSEDED response to that original PATCH; then re-read current configuration before a new reviewed intent. A locally proved never-dispatched intent may be released. Pending/uncertain state survives dialog reset; authority/account/tab/reload changes never resume, copy or automatically replay a mutation. Retired scopes clear private draft/payload and detach presentation; a known unresolved original command remains uncertain if its exact payload or authorized observation is unavailable. Do not guess a reconstructed payload or treat a current list row, lost local observation or absent outcome as replacement permission. This recovery uses existing counter/audit/lock owners; no cancellation endpoint or negative-result history table is introduced.

## Wallet, Ledger and Finance

`WalletView`: employeeId, serverNow, existing walletComponents, membership, purchaseEligibleAmount, `withdrawalFunds` `{eligibleNonReferral,eligibleReferral,total,lockedReferral}`, restrictions `{accountUnavailable,withdrawalsBlocked}`, and `withdrawalExecutionReady:false` for P04. Funds eligibility is not a request/address/fee/limits approval. All owned components persist at expiry; only unreserved referral withdrawal eligibility changes. Pending work is not credit. AdminWalletView adds permitted employee identity, no credentials/provider/private storage data.

`LedgerFilter`: page/limit, optional kind from existing operation kinds, origin from existing financial origins, source REFERRAL/NON_REFERRAL, direction CREDIT/DEBIT/NEUTRAL, from/to ISO instants with from<=to (inclusive lower/exclusive upper). Admin additionally accepts optional employeeId and trimmed q max150 characters. Preserve finance search by matching permitted employee name, safe operation/reference IDs and the approved title/origin/source display-label dictionary; SQL predicates apply before count/summary/page. Do not search internal hashes/secrets or only loaded rows. Unknown/array/malformed filters rejected. Source filter uses EXISTS, never duplicates operation row. Direction derives signed ownership delta, not magnitude; filters never grant permission.

`LedgerRow`: operationId, recordedAt, kind, origin, direction, magnitude, signedOwnershipDelta, selected source movements, safe reference label. Employee excludes actor secrets/internal namespace/key/hash; admin may include permitted employee/actor identity and separately audited correction reason/reference. `LedgerDetail` adds full same-operation source movements and safe saved terms, not raw FinancialOperation/JSON or unrelated account data.

`LedgerPage`: items, pagination, summary `{scope:"FILTERED_OPERATIONS",credits,debits,net}` and serverNow. `AdminFinancePage` additionally includes declared `walletTotalsScope` for current wallet totals (all employees or selected employee), exact available/reserved/referral/non-referral/owned totals and permitted identities. Time/kind/origin filters affect operation summary, not historical reconstruction of current wallet totals. Totals cover every filtered record, not current page. net is exact signed credits-debits; neutral reserve/release contributes neither. No invented future events or reward reversal. Avoid summing debit once per joined award.

`AdminFinancePage.summary` additionally requires `neutralOperationsCount`, a nonnegative safe integer counting distinct RESERVE/RELEASE operations matching every active operation filter before pagination. The existing neutral-operation metric uses this server count. Source posting joins must not multiply operations; use the same filtered operation set as summary/count/page. Direction CREDIT/DEBIT filters therefore yield zero neutral operations from a successful query. Rows, pagination and summary share the plan's RepeatableRead observation. Page changes preserve the same-scope summary; changed filters recompute it. A malformed/missing count is unavailable, never a zero fallback. Neutral operations contribute zero to credits/debits/net; employee LedgerPage need not acquire this admin-only metric.

Aggregate money uses a separate proposed canonical signed/unsigned decimal schema with at most 38 micro-unit digits and no float, comma/exponent or redundant fractional zeros. It is read-only/nonspendable and never accepted by a command. Single-wallet/operation amounts keep existing int64 bounds. Exceeded aggregate range produces safe unavailable error, never truncated/zero total.

## Referral Projections and Lists

`EmployeeTeamSummary`: self root `{id,fullName,referralCode}`, serverNow, current rates/version, member/paid counts for L1-L5 and exact own earned totals by level/all time. Own invite identity comes from P02, never fixtures. `EmployeeMember`: id, fullName, joinedAt, relative level, current package code/null and viewerEarnedFromMember. No email, member wallet/earnings or sponsor internals. Employee commissions have decisionId/purchaseId/date/level/buyer safe display/rate/base/award and own-beneficiary scope; AWARDED/ELIGIBLE_ZERO only, zero history clearly labeled.

Admin root identity adds permitted email; admin summary includes root separately, L1-L5 counts with `levelCountsScope:"ROOT_UNFILTERED"` and SQL-derived deeper descendant count. Admin member may expose permitted email and bounded root-to-member path (max five displayed steps), never credentials. Admin member q is trimmed max150 characters, matching descendant name/email/ID within the selected root before SQL count/page; `pagination.total` and member list scope are FILTERED_MEMBERS, distinct from full-root level counts. Root search is a separate control. Admin commission list explicitly treats selected root as recipient/beneficiary and may include SKIPPED reasons and saved eligibility projection; it must not silently combine every descendant's earnings. Current rates differ from saved event rates.

`CommissionFilter`: page/limit, optional level 1..5, from/to instants, optional buyerId; admin additionally decision AWARDED/ELIGIBLE_ZERO/SKIPPED. SQL scopes beneficiary/root and filters before count/summary. Root search q is trimmed max 150 characters (empty selects first bounded page), searches name/email/referralCode, only employee roots; no full-tree response.

Every list defaults page=1/limit=25, max 100, validates safe offset; totalPages=0 on zero results. Histories order occurredAt DESC,id DESC; member/root lists use stable joinedAt/id plus level where appropriate. Rows/count/summary share one RepeatableRead observation. Lists are live across requests: inserts can move offsets; no frozen snapshot token is promised. Return empty items with true count/meta for out-of-range page and allow scoped recovery/first-page refresh. Every quiescent permitted record is reachable. Page changes/root/filter changes cannot disclose prior scope or enable stale detail actions.

## Observable Failures

| Status/code                                                                          | Meaning / client action                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400 VALIDATION_ERROR or LEDGER_INVALID_INTENT                                        | Rejected schema/intent, field paths prefixed body/query/params; no business effects                                                                                                                                         |
| 401 UNAUTHORIZED                                                                     | Missing/revoked/expired/currently unavailable session; no committed command effects from this rejected request; P04 still does not use automatic refresh/replay                                                             |
| 403 FORBIDDEN or LEDGER_FORBIDDEN                                                    | Current role/action denial; hide protected scope and require new allowed authority observation                                                                                                                              |
| 404 NOT_FOUND                                                                        | Missing/foreign private resource; no existence disclosure                                                                                                                                                                   |
| 409 proposed PURCHASE_QUOTE_STALE / PURCHASE_TRANSITION_DENIED / CONFIGURATION_STALE | Stale reviewed state, forbidden transition or version; no partial effects, preserve draft/review fresh terms explicitly                                                                                                     |
| 409 proposed CONFIGURATION_SUPERSEDED                                                | Original configuration PATCH only: current authority plus fresh matching actor/target lock barrier finds no saved command and a greater target version; terminal for that unchanged intent, then reread before another edit |
| 409 LEDGER_IDENTITY_CONFLICT                                                         | Changed actor/key/business intent; no replacement key to bypass                                                                                                                                                             |
| 409 LEDGER_INSUFFICIENT_FUNDS / LEDGER_AMOUNT_BOUNDS                                 | Funding/range failure, no partial effects                                                                                                                                                                                   |
| 409 ledger transaction conflict/unresolved codes                                     | Bounded conflict exhaustion; authoritative reconciliation before another financial intent                                                                                                                                   |
| 429 current limiter envelope                                                         | Request rejected; no hidden automatic financial replay                                                                                                                                                                      |
| 500 LEDGER_INTERNAL or safe internal error; network/timeout/malformed success        | Client cannot infer failed commit; retain original intent, read reconcile, no fake success/zero/refund                                                                                                                      |

New domain codes above are proposed and must be added/tested with production error owners; existing codes/statuses were verified in current error classes. Diagnostic output may carry correlation/operation IDs and bounded safe failure class, never full amounts/eligibility payloads/secrets. Maintain OpenAPI and producer/consumer tests together.
