## Session Authority and Cookie Ordering

1. Browser lifecycle starts checking, never from fixture or storage identity. A current validated /users/me response supplies the allowed account; raw login/refresh output cannot independently bypass role/status/session checks.
2. A protected path/check generation change derives blocked state before children mount, including persistent App Router layouts. Fresh route-entry, focus/reconnect/manual checks use one shared restoration/refresh owner. A stale cached user is display data, not renewed permission.
3. Scope read/query/handler results by non-secret local epoch and current account/role; authority-check results also match check generation. Pass AbortSignal through reads. Every obsolete token/data/error/navigation completion is discarded even if cancellation could not stop the work.
4. Confirmed terminal authentication denial retires private authority immediately. Wrong-role, inactive/unverified and unavailable/contract-error states never mount private children. A policy/CSRF 403 cannot itself prove session revocation: deny its command and reconcile current authority safely.
5. Teardown blocks render/handlers first, retires epoch/check, cancels private reads, clears private caches/errors/forms/command state and memory token, and coordinates pending cookie operations. It must not admit B while unresolved A work can regain authority.
6. Use one central refresh path for restoration and authenticated 401 handling. Parse its response before token admission, preserve cookie/CSRF mechanics, and never share its memory token with SSR or storage.
7. Login, refresh, logout, logout-all, reset and password change all write/clear cookies; serialize them with one non-secret same-origin Web Lock and the persistent barrier defined below. Do not nest acquisition across interceptor/hook callers. Use BroadcastChannel/storage events only for non-secret retirement/revalidation hints; recipients never treat a message as authority. Unsupported coordination/storage produces approved unavailable feedback instead of unsafe fallback.
8. JS epoch suppression cannot reverse browser Set-Cookie. Preserve the barrier until its live owner observes a complete terminal HTTP response. Cancellation, timeout or lock reacquisition cannot establish that result. Quarantine private state and block further cookie writes while unresolved; a current-authority response alone cannot release an abandoned write. A different-account sign-in requires preceding cookie settlement and permitted authority teardown/reconciliation, never only clearing a local token.
9. Same-origin tabs retire/revalidate on hints and their next authoritative check. Separate browser/device contexts retain independent sessions. Ordinary logout affects only its server session; reset/change/logout-all affect target account sessions. Shared reset may clear unrelated browser cookies without revoking that unrelated account's other server sessions.

App Router navigation uses sanitized router.replace/links, with default /employee for USER and /admin for ADMIN. Reject external/protocol-relative/backslash/control/malformed paths, wrong-role/auth-loop destinations and decoded credential-bearing queries. Never carry action link credentials into return navigation. History cleanup may use Next-supported native replaceState for the same route; it is not an auth action or browser reload.

### Cookie-write barrier and owner loss (U1)

- The browser-only session runtime owns one fixed localStorage record: strict `{version:1, operationId:opaque, state:pending|uncertain}` with bounded fields. It contains no identity, credentials/hashes, session ID, request payload/URL, return target or timestamp/TTL. It can only block work. All P03 cookie-writing callers use the same exclusive Web Lock and canonical frontend origin; storage does not provide its own locking.
- Before dispatch, acquire the lock and read/validate the record. Any inherited pending/uncertain, malformed/unknown-version or unreadable record prevents dispatch and private restoration. With no barrier, synchronously write/read back the pending operation ID before sending HTTP; storage failure prevents sending. Protected restoration/check generations inspect this coordination state before admitting private work. Cross-tab hints promptly retire views; authority still requires the server check.
- Keep the original HTTP observer/operation owner independent of component/dialog lifetime and any UI deadline. Only that live owner, still holding the lock and matching the stored operation ID, can remove the record after receiving its complete terminal HTTP response. A complete HTTP denial or malformed application payload may end cookie-order uncertainty, but cannot claim mutation success or supply identity. Release ordering and parsed business success are separate; revalidate authority before private admission and suppress obsolete UI/token/navigation callbacks.
- Abort, network/CORS failure, page unload/close, missing owner and deadline expiry leave the record pending/uncertain. Reacquiring the released lock, receiving `/users/me`, observing a revoked session, waiting, or clearing local memory does not prove an older response cannot later apply cookies. No generic finally deletion, automatic TTL, lock stealing, mutation replay or user-facing cookie/storage-reset shortcut is allowed. A UI deadline may show uncertainty while a still-live owner continues observing; its later terminal response can satisfy the normal release criteria.
- After actual owner loss, surviving/new tabs and reloads sharing the cookie/storage context remain unavailable for private restoration and cookie-changing commands. Existing public non-cookie preview/email-recovery remains reachable without claiming the uncertain action's outcome. C2 Arabic feedback explains use of a wholly separate browser profile or independently isolated private browsing session. A normal new tab, reopening the same profile, or another private window sharing its existing private session is insufficient. The new context starts with independent cookies/storage, then explicitly signs in and validates current authority. It does not revoke any session abandoned work may have created.
- This frontend-only protocol assumes supported, intact storage and one canonical frontend origin for the relevant cookie context. It is not a crash-durable server fence. Storage deletion/eviction, cookie-only clearing, another frontend origin sharing cookies and host compromise are outside its safety proof and must not be presented as safe same-context recovery. Existing P02 endpoints have no operation-status/fencing primitive; transparent recovery of an abandoned write is unavailable within P03 scope.

Acceptance must cover terminal success/denial release, a UI deadline followed by live-owner settlement, real delayed login/refresh/logout/reset/change responses with holder reload/close, surviving-tab lock reacquisition, new-tab/reload persistence, zero replacement cookie writes/private reads while quarantined, unsupported/malformed storage, isolated-context recovery and zero secrets in the record. Mock tests establish transitions; real browser tests establish unload/cookie/storage behavior.

## Credential Flow and Private Errors

- Client captures a bounded credential once from the current browser URL into a short-lived flow owner, then cleans current history before incidental navigation/requests. Do not pass it through server-rendered props or retained Query/Mutation options/metadata. No token/hash key, storage persistence or analytics/logging.
- Opening/preview/reload only validates. A clean reload without credential/context shows C2 missing-link/recovery input; it does not restore secrets from storage. Preview exposes only valid:true; never show decoded subject/role/expiry as authoritative.
- Explicit confirmation/submission alone sends verification/reset/acceptance. Exact server expiry/current purpose/generation/issuer checks prevail over earlier preview. Success requires valid committed response; malformed/unknown result is not apparent success.
- Imperative transient hooks invoke the existing adapters with safe pending/outcome state. No secret Mutation variables/data/error/context/closures retained after request settlement. Guard pending work outside dismissible components so close/remount cannot resubmit. Clean live input on completion/dismissal/identity teardown; preserve recoverable input only in its active authorized form after correctable denial.
- Safe transport rejection occurs before Query/command caches: controlled category/status/code and known editable field mappings only, optionally a safely validated request identifier. Do not retain raw message/config/headers/body/URL/stack/cause/parser issues. Credential flow never logs payloads; contract failures are bounded and non-retryable.
- Credential routes emit no-referrer; verify actual browser/referrer behavior. Development request logs suppress credential routes; browser reports/artifacts exclude secrets. Legitimate token query HTTP requests retain the existing protocol; no zero-network-token claim is made.

## Commands, Reconciliation and Management

| Event                           | Observable state and recovery                                                                                                                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Correctable form denial         | Safe Arabic error/known field feedback; no success; appropriate active input retained for correction.                                                                                                      |
| Command pending/dialog remount  | In-flight guard persists; duplicate submission blocked; pending/focus/dismissal behavior stays usable without hiding unknown effects.                                                                      |
| Logout response lost            | Private content quarantined; cookie barrier retained. Only original terminal observation releases ordering; after owner loss use isolated-context recovery. No confirmed-revocation claim or blind replay. |
| Password response lost          | No success solely from revoked session/invalid token. Retain cookie barrier; after owner loss fresh sign-in/recovery uses an isolated context. Never automatically replay a one-time credential.           |
| Admin stale/concurrent denial   | Refresh validated detail/list, preserve unrelated dirty reason/input; current version wins; no newer-state overwrite or fabricated actor/time.                                                             |
| Admin mutation success          | Reconcile affected same-account list/detail/query scopes from validated result/refetch; do not globally clear unrelated state.                                                                             |
| Invitation delivery uncertainty | Disposition and delivery remain separate; acknowledge only evidence available. Lost issuance without ID remains uncertain if bounded reads cannot resolve it.                                              |
| Session switch/revocation       | Old data/credentials/errors/late callbacks cannot enter new scope. Restoration does not revive server-revoked sessions; fresh sign-in required.                                                            |

No optimistic admin creation/status/acceptance, automatic uncertain mutation retry or offline replay. Reasons come from entered input; confirmed:true follows an actual reviewed click; versions come from current validated target, never fixtures. Reissue/revoke follow server eligibility/cooldown/generation, not client-time guesses. Unsupported editing/global filtering/activity/counts retain C3 treatment. No current-page totals or unbounded fetch substitutes for absent backend capability.
