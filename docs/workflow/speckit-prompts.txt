HOW THE OWNER USES THIS PACK

1. Run CONSTITUTION once for the project. Amend it only for an explicitly
   approved project-wide policy change. Do not run it again for each phase.
2. Select PHASE_ID, for example P01. It refers to the OSCAR roadmap, not to a
   numbered section inside generated tasks.md.
3. For that phase, run SPECIFY, CLARIFY, PLAN, CHECKLIST, TASKS, ANALYZE,
   IMPLEMENT, and CONVERGE in that order.
4. Review findings and fix the owning specification or design artifact before
   implementation when required. Do not skip unresolved critical findings.
5. If CONVERGE appends remediation tasks, run IMPLEMENT for those task IDs only,
   then CONVERGE again. Never execute the next roadmap phase automatically.
6. Repeat steps 2-5 for the next roadmap phase after its prerequisites pass.

If IMPLEMENT is scoped to a batch, repeat it for remaining dependency-safe batches
until this phase's implementation tasks finish before claiming full convergence.
Incomplete batches are not complete roadmap phases.

PHASE_ID is a natural-language prompt binding, not a Spec Kit CLI flag.
The Codex integration installed here exposes $speckit-* skills. Other tools may
use a different command form; verify their registration instead of guessing.
TASK_SCOPE is required for IMPLEMENT. Supply explicit task IDs, an explicitly
selected dependency-safe batch, NEXT_DEPENDENCY_SAFE_BATCH, or the consciously
selected value ALL_ACTIVE_PHASE_TASKS. NEXT_DEPENDENCY_SAFE_BATCH means inspect
dependencies, identify/report the next exact IDs, then execute only those IDs.
ALL_ACTIVE_PHASE_TASKS means all current approved tasks in this phase only, using
small internal batches; it never means the complete roadmap. If TASK_SCOPE is
missing or ambiguous, ask before implementing rather than assuming all tasks.
Values supplied in the owner's launcher bind the placeholders below. Do not ask
the owner to repeat PHASE_ID or TASK_SCOPE when they already supplied them.

F. Financial and security invariants

- Treat all clients, uploaded files, provider responses and job messages as
  untrusted. Enforce current role, status, ownership, entitlement and state
  transitions on the server. Hiding a control is not authorization.
- USDT only. Use exact integer micro-USDT arithmetic and validated decimal
  strings at JSON boundaries. Never accept client-calculated balances, rewards,
  package entitlement, fees or commission amounts as financial authority.
- Keep an auditable source-aware append-only ledger and atomic available/reserved
  balances.
  Database constraints, transactions, conditional transitions and idempotency
  prevent duplicate credits, commissions, reservations and settlement.
- An upgrade debits the full target package price; its commission base is the
  positive difference from the previous subscription's snapshotted price. These
  are different calculations. Preserve exact formulas and source allocation.
- Purchases consume unreserved referral funds first, then other unreserved funds.
  Withdrawals reserve eligible non-referral funds first, then eligible referral
  funds. Cancellation/refund releases the identical recorded source allocation.
  Neither path may spend reserved funds or turn locked commissions into deposits.
- Task submission does not credit available balance. Only final admin approval
  posts its snapshotted reward, exactly once. Pending work is not spendable money.
- Use the server-authoritative Asia/Baghdad business calendar. Subscription work
  dates and counted withdrawal hours exclude Saturday/Sunday; confirmed deposits
  still credit every day. Task windows and all boundaries follow PLAN.md.
- Deposits credit once after verified successful confirmed token transfers,
  including ownership of the destination address, configured network/token,
  amount and canonical event identity. A user-entered public TxID alone is not
  proof that the deposit belongs to that user. Deposits have no 72-hour hold.
- Withdrawal scheduling is durable. Redis/queues may trigger execution, but
  PostgreSQL is authoritative for due time, state, reservation and attempt data.
  Workers and retries must tolerate duplicates, races, crashes and restarts.
- At most one active withdrawal per user, including SCHEDULED, SIGNING, SUBMITTED
  and UNKNOWN categories. UNKNOWN is not terminal. Preserve reservation sources
  on refund/cancellation. A possibly submitted transfer stays reserved until
  reconciled; an uncertain result must never cause blind repayment or refund.
- Persist the signed payout attempt and transaction identity before broadcasting.
  Reconcile canonical results and reuse the same safe attempt as specified in
  PLAN.md; a retry is not permission to sign a fresh payment.
- Isolate signing credentials/private keys from the browser, public API routes,
  logs and fixtures. Preserve custody, backup, recovery and restore controls.
  Do not publish unbacked deposit addresses or restore financial operation
  without the roadmap's reconciliation/fencing procedure.
- Protect authentication, secrets, private proof files and administrative actions.
  Audit privileged changes without logging secrets or private financial payloads.
- Preserve approved business decisions, including no admin 2FA/dual approval,
  and explicitly report their residual risks. Never claim guaranteed immunity
  from hacking or misuse. Do not weaken compensating controls to simplify work.
- Detailed formulas, dates, fees, eligibility, limits, proof retention and state
  machines come from PLAN.md. Do not reopen settled decisions or copy stale UI
  behavior. A genuine newly discovered financial ambiguity requires clarification.
